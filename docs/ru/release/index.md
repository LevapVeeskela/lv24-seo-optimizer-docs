# Релизы и обновление

Текущие релизы:

| Продукт | Версия | Примечания |
|---|---|---|
| Движок | `lv24-seo 0.5.1` | Bugfix-релиз; без миграции схемы, новых CLI-команд и MCP-инструментов |
| Приложение | `0.2.1` | Патч: токен Метрики, общий keychain с CLI; включает движок 0.5.1 |

Версии приложения и движка независимы, но приложение закрепляет точный движок и
отказывается от версии ниже минимума.

## Движок 0.5.1

Это bugfix-релиз линии 0.5.x. Он закрывает блокеры, найденные после 0.5.0: сбой
провайдера мог навсегда пометить запись дубликатом, текст обхода хранился без
ограничения, аннотации MCP объявляли два инструмента локального состояния read-only, а
несколько документированных лимитов были недостижимы.

Что изменилось:

- **Повторы write-гейта.** Apply занимает слот идемпотентности как `pending`, вызывает
  провайдера и только потом переводит заявку в `sent`. Если провайдер выбрасывает
  исключение, pending-заявка освобождается до повторного проброса исходной ошибки,
  поэтому повтор с тем же планом разрешён. Завершённая или выполняющаяся заявка — всё
  ещё дубликат.
- **Ограничение текста обхода.** `PageData.text` хранит не более 20 000 символов, а
  `word_count` по-прежнему считается по полному видимому тексту. Извлечение ссылок,
  JSON-LD, hreflang и подсчёт слов читают полный документ.
- **Аннотации MCP.** `seo_crawl_site` и `seo_weekly_report` сохраняют локальные снимки,
  поэтому у них `writes_local_state: true` и `readOnlyHint: false`. Состояние
  провайдера они не меняют и confirm-токен не требуют.
- **Достижимые лимиты.** Обнаружение sitemap использует бюджет тела на запрос, поэтому
  документированный лимит 50 МБ на документ достижим; обычные страницы сохраняют 5 МБ, а
  протокольный лимит 50 000 URL не изменился. `stats` и `report weekly` отклоняют
  `--days` больше 3 660 с `INVALID_INPUT`.
- **Сбои недельного сборщика.** Сигнатура сборщика проверяется один раз до вызова.
  `TypeError` внутри совместимого сборщика больше не проглатывается; команда возвращает
  `INTERNAL` и не сохраняет снимок.
- **Усечение GSC.** Последняя страница, которая ровно заполняет лимит 50 000 строк,
  считается полной, а не усечённой. `rows_cap_50000` сообщается только при наличии ещё
  одной строки.
- **Мелкие исправления.** Windows npm-лаунчер игнорирует `.cmd`-шимы; окна MCP по
  умолчанию используют `report.timezone`; многомерные ключи метрик кодируются в JSON;
  отрицательные лимиты хранилища ограничиваются нулём; `report diff --markdown` пишет
  предупреждения в stderr; установка планировщика чинит повреждённые managed-блоки;
  `auth status` включает Yandex Metrika.

Проверки этого релиза:

| Проверка | Результат |
|---|---|
| Офлайн-набор тестов | 1114 passed, 1 skipped (1115 collected) |
| `ruff check` | Чисто |
| `ruff format --check` | Чисто |
| `mypy src` | Чисто |

Новые регрессионные тесты покрывают освобождение и повтор write-гейта, лимит текста 20k
с точным `word_count`, аннотации MCP, бюджет sitemap 50 МБ, отклонение `--days`,
несовпадение сигнатуры сборщика и внутренний `TypeError`, точное заполнение лимита GSC,
случай `.cmd`-лаунчера Windows, окна с настроенной таймзоной, коллизии ключей метрик,
отрицательные лимиты, предупреждения в stderr, починку блоков планировщика и
аутентификацию Metrika.

Известные ограничения 0.5.1:

- У `pending`-заявки записи, оставшейся после падения, нет TTL; она считается
  выполняющейся, пока оператор её не освободит. Это намеренно: ложный повтор может
  продублировать запись у провайдера.
- Ограничение текста обхода — это граница хранения, а не граница парсинга.
- Бюджет sitemap 50 МБ действует на документ; индекс sitemap может потратить его на
  несколько дочерних документов в пределах лимита 20 документов.
- MCP-клиенты, которые смотрят на `readOnlyHint`, теперь могут запросить подтверждение
  перед `seo_crawl_site` или `seo_weekly_report`.

## Артефакты приложения 0.2.1

`0.2.0` был первым мультиплатформенным релизом; `0.2.1` — текущий патч. Он исправляет
токен Яндекс Метрики в настройках и окне секретов и делает общий keychain с CLI явным:
токен, введённый через `lv24-seo auth set` в терминале, виден в приложении, и наоборот.
GitHub заменяет пробелы в именах артефактов точками; страница релиза — источник истины
для точных имён Linux-файлов.

| Артефакт | Платформа | Назначение |
|---|---|---|
| `LV24.SEO.Optimizer_0.2.1_x64-setup.exe` + `.exe.sig` | Windows x64 | NSIS-установщик для пользователя; подписанный пакет обновления |
| `LV24-SEO-Optimizer_0.2.1_x64-portable.zip` | Windows x64 | Portable-сборка; manual-only |
| `LV24.SEO.Optimizer_0.2.1_aarch64.dmg` | macOS Apple silicon | Первая установка |
| `LV24.SEO.Optimizer_0.2.1_x64.dmg` | macOS Intel | Первая установка |
| `LV24.SEO.Optimizer_0.2.1_aarch64.app.tar.gz` + `.sig` | macOS Apple silicon | Подписанный пакет обновления |
| `LV24.SEO.Optimizer_0.2.1_x64.app.tar.gz` + `.sig` | macOS Intel | Подписанный пакет обновления |
| `LV24.SEO.Optimizer_0.2.1_amd64.AppImage` + `.AppImage.sig` | Linux x64 | AppImage; подписанный пакет обновления |
| `LV24.SEO.Optimizer_0.2.1_amd64.deb`, `LV24.SEO.Optimizer-0.2.1-1.x86_64.rpm` | Linux x64 | Установка менеджером пакетов; manual-only |
| `latest.json` | Все | Подписанный манифест обновлений |
| `SHA256SUMS.txt` | Все | SHA-256 каждого опубликованного артефакта |

Установщику Windows нужны Windows 10/11 x64 и runtime WebView2; NSIS-установщик может
его скачать, portable ZIP — нет. Linux-пакеты собраны на Ubuntu 22.04 с базой glibc 2.35
и только для x64. macOS требует macOS 13 или новее; используйте `aarch64` DMG на Apple
silicon и `x64` DMG на Intel.

## Матрица автообновления

| Пакет | Обновление в приложении | Что происходит |
|---|---|---|
| Windows NSIS | Да | Скачивает подписанный setup `.exe`, запускает в passive-режиме, перезапускает |
| macOS `.app` | Да | Скачивает подписанный `.app.tar.gz`, заменяет приложение, перезапускает |
| Linux AppImage | Да | Скачивает подписанный AppImage, заменяет его, перезапускает |
| Windows portable ZIP | Нет | Settings ведёт на страницу релиза; скачайте и распакуйте новый ZIP |
| Linux deb | Нет | Settings ведёт на страницу релиза; обновление менеджером пакетов |
| Linux rpm | Нет | Settings ведёт на страницу релиза; обновление менеджером пакетов |
| MSI | Нет | MSI не выпускается; установка MSI считается ручной |
| Неизвестный пакет | Нет | Settings ведёт на страницу релиза |

Manual-only сделано намеренно. Установкой deb или rpm владеет база пакетов; MSI этот
проект не выпускает, и NSIS-пакет обновления не может его заменить; у portable ZIP нет
установщика, и он может лежать на съёмном носителе. Приложение сообщает тип установки и
отключает встроенный установщик для таких случаев. Оно не делает вид, что ручной пакет
обновился.

Путь Windows NSIS проверен end-to-end: установленная сборка `0.2.0` обнаружила `0.2.1`,
скачала и проверила подписанный пакет, установила его в passive-режиме, перезапустилась и
показала `0.2.1` с готовым движком `0.5.1`.

## Релизный конвейер

Workflow приложения ручной и требует владельца. У него нет триггеров push,
pull-request или tag. Владелец запускает **Actions → Desktop build → Run workflow** и
подтверждает окружение `desktop-release`; запуск не владельцем пропускается.

| Вход | По умолчанию | Значение |
|---|---|---|
| `engine_version` | `0.5.1` | Точный движок в sidecar |
| `signed` | `false` | Запросить подпись/notarization ОС; в zero-spend репозитории не настроено |
| `publish` | `false` | Создать GitHub release после успешной матрицы |
| `tag` | Пусто | Тег `vX.Y.Z`; обязателен при `publish=true` |

Значение по умолчанию совпадает с пином `0.2.1`. Релизный гейт отклоняет
несоответствие манифеста, если передана другая версия.

| Runner | Target | Пакеты |
|---|---|---|
| `windows-latest` | `x86_64-pc-windows-msvc` | NSIS |
| `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | AppImage, deb, rpm |
| `macos-15` | `aarch64-apple-darwin` | DMG + app |
| `macos-15-intel` | `x86_64-apple-darwin` | DMG + app |

Все runners — стандартные GitHub-hosted. Платные larger runner, минуты, хранилище и
сервисы подписи не используются. Артефакты сборки хранятся 7 дней; GitHub release —
долговечный канал распространения.

## Пин sidecar и контрольные суммы

Релизный sidecar — дерево PyInstaller **onedir**, собранное на соответствующем хосте;
PyInstaller не кросс-компилирует. Версии движка, Python, Pydantic, Typer и PyInstaller
закреплены в `scripts/cli-checksums.json`. `0.2.1` закрепляет движок `0.5.1`, Python
`3.12`, Pydantic `2.14.3`, Typer `0.29.0` и PyInstaller `6.22.3`.

Вывод PyInstaller onedir не воспроизводится побайтово. Поэтому политика контрольных сумм
разделена:

- **Локальная релизная сборка — строгая.** `scripts/verify-sidecar.mjs` должен совпасть
  с закоммиченными SHA-256 и размером; `--write` обновляет пин после ревью. Пин `null`
  означает «ещё не проверено», а не «проверено».
- **Пересборка CI — rebuild-aware.** Build job запускает верификатор с `--no-hash` и
  записывает фактический SHA-256 в `release/sidecar-checksums-<target>.json`.
- **Релизный гейт — по отчёту.** Release job требует валидный отчёт для каждой
  поставляемой цели: совпадение имени target, `hashPolicy: "rebuild"`, `ok: true`,
  64-символьный hex-хеш, положительный размер и точную версию движка.

Отчёты контрольных сумм — доказательство CI, а не релизные артефакты. `SHA256SUMS.txt`
покрывает установщики, пакеты обновлений, подписи и `latest.json`; исполняемый файл
sidecar находится внутри этих пакетов и отдельно не указан. Пользователи, ставящие
вручную, проверяют скачанный артефакт по `SHA256SUMS.txt`.

```bash
node scripts/verify-sidecar.mjs \
  --root src-tauri/engine \
  --target x86_64-pc-windows-msvc \
  --engine-version 0.5.1
```

## `latest.json`, подпись и публикация

Подписи обновлений используют бесплатный ключ Ed25519/minisign, отдельный от подписи кода
ОС. Публичный ключ встроен в приложение; приватный — секрет репозитория, передаваемый
только на шаг сборки. Включён `requireSignedVersion`, поэтому объявленная версия
привязана к подписанному пакету. Обновление принимает только версию выше текущей, поэтому
откатиться нельзя.

`scripts/stage-release-assets.mjs` выравнивает и нормализует имена пакетов и пишет
метаданные `updater-<platform>.json`. `scripts/merge-latest-json.mjs` объединяет их в
`latest.json`:

- обязательные generic-ключи: `windows-x86_64`, `linux-x86_64`, `darwin-aarch64`,
  `darwin-x86_64`;
- алиасы пакетов, которые проверяет updater: `windows-x86_64-nsis`,
  `linux-x86_64-appimage`, `darwin-aarch64-app`, `darwin-x86_64-app`;
- опциональные `linux-x86_64-deb` и `linux-x86_64-rpm` только если Tauri создал их
  подписи;
- каждый URL ведёт под `releases/download/<tag>/`;
- каждая подпись сверяется с файлом `.sig` на диске;
- каждый указанный артефакт должен существовать;
- notes берутся из `docs/releases/<version>.md`, если файл есть.

Релиз сначала создаётся как **draft**. Артефакты загружаются, пока он черновик, а
`latest.json` — последним; затем job публикует через `gh release edit --draft=false` и
проверяет удалённые имена. `releases/latest/download/latest.json` резолвится только для
опубликованного релиза, поэтому пользователи не видят частично загруженный манифест.
Повторный запуск переиспользует существующий draft, очищает его артефакты и отказывается
перезаписывать опубликованный релиз.

## Закрепление версий

Версия приложения должна совпадать в `package.json`, `src-tauri/tauri.conf.json`,
`src-tauri/Cargo.toml`, Git-теге и заголовке релиза. Пин движка живёт в
`scripts/cli-checksums.json`; workflow передаёт `engine_version` явно, а релизный гейт
требует совпадения с манифестом.

`MIN_ENGINE_VERSION` в `src-tauri/src/commands.rs` в текущем исходнике равен `0.5.1`.
Оболочка принимает движок не старее этого и помечает старый offline с уведомлением.
Более новый движок проходит гейт, но не является протестированным пином релиза.
Development-сборка может использовать `LV24_SEO_BIN` с другой версией; UI помечает его
external и всё равно проверяет минимум. Движок из `PATH` используется только при
`LV24_SEO_ALLOW_PATH_ENGINE=1`.

## Однократное обновление с 0.1.0

У `0.1.0` нет updater, endpoint и публичного ключа. Он не может найти или установить
`0.2.1`. Скачайте и установите `0.2.1` вручную один раз (NSIS-установщик или portable
ZIP в Windows). После этого установка `0.2.1` может автоматически обновляться до
следующих релизов, если использует пакет с поддержкой автообновления.

## Откат

Автоматического отката нет. Откат — это ручная установка более старого релиза.

| Сбой | Реакция |
|---|---|
| Плохой установщик, но рабочее приложение | Выпустить исправленный патч; не перезаписывать артефакты под тем же тегом |
| Плохой `latest.json` | Выпустить исправленный патч; draft-гейт не даёт частичному манифесту стать видимым |
| Компрометация ключа updater | Ротировать ключ, выпустить ручной релиз с новым публичным ключом; автообновление не переживёт ротацию |
| Регрессия движка | Закрепить предыдущую версию движка, пересобрать и выпустить патч |
| Нужна старая сборка приложения | Установить вручную; updater отказывается от понижения |

Не перемещайте и не переиспользуйте опубликованный тег. Держите артефакты предыдущего
релиза доступными для отката. Если endpoint нужно отключить, выпустите ручной релиз и
задокументируйте это.

## Проверка загрузки

`SHA256SUMS.txt` покрывает каждый опубликованный артефакт. Проверьте файлы, которые
собираетесь устанавливать:

```bash
sha256sum -c SHA256SUMS.txt --ignore-missing
```

В macOS есть `shasum -a 256 -c SHA256SUMS.txt`. В Windows сравните
`Get-FileHash <file> -Algorithm SHA256` с соответствующей строкой. Не запускайте файл,
хеш которого не совпал.

По умолчанию пакеты ОС не подписаны (Windows, Linux) или подписаны ad-hoc (macOS). Подпись updater
аутентифицирует обновления, а не первую ручную загрузку. Предупреждения SmartScreen и
Gatekeeper ожидаемы; проверьте контрольную сумму и используйте документированный
**More info → Run anyway** или **Open Anyway**. Не отключайте эти защиты глобально.

См. [Безопасность и приватность](/ru/security/) для доверия к updater и [Архитектура](/ru/architecture/) для устройства sidecar.
