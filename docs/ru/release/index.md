# Релизы и обновления

Текущие релизы:

| Продукт | Версия | Дата | Примечания |
|---|---|---|---|
| Движок | `lv24-seo 0.11.0` | 2026-11-17 | Глубина чтения по всем платформам: инспекция и карты сайта GSC, события/карты/переобход Яндекса, страницы/трафик/обход/URL/связки Bing, органическая Метрика, аудиты и история CWV; 24 команды CLI и 12 инструментов MCP |
| Приложение | `0.9.0` | 2026-11-17 | Экран Diagnostics только для чтения с пятью вкладками и 18 командами из белого списка, движок 0.11.0 и `MIN_ENGINE_VERSION` 0.11.0 |

Версия приложения и версия движка независимы, но приложение закрепляет точный движок и отказывается работать с версией ниже минимальной. `0.9.0` включает `0.11.0` и требует минимум `0.11.0`, поэтому установленный движок `0.10.x` считается несовместимым.

## Движок 0.11.0

Выпущен 2026-11-17. Каждая поддерживаемая платформа получает API чтения, которые раньше были
только в адаптере, частичными или отсутствовали. В CLI теперь 24 команды верхнего уровня;
поверхность MCP остаётся в 12 инструментов, схема SQLite — версия 4.

Что изменилось:

- **URL Inspection в GSC.** `gsc inspect --url ABS [--language en-US] [--config ABS] [--json]` подключает URL Inspection целиком. Результат отображает полный `indexStatusResult` (`verdict`, `coverageState`, `robotsTxtState`, `indexingState`, `lastCrawlTime`, `pageFetchState`, `googleCanonical`, `userCanonical`, `crawledAs`, `sitemap[]`, `referringUrls[]`), `richResultsResult` (`verdict`, `detectedItems[].items[].issues[]`) и `inspectionResultLink`. `--language` локализует человекочитаемые состояния. Ограничения: `one_url_per_call`, `url_inspection_quota_2000_per_day`, `inspection_reflects_last_crawl` — это отчёт о последнем обходе, а не живой тест.
- **Карты сайта GSC.** `gsc sitemaps [--sitemap-index URL]` и `gsc sitemap --path URL` отображают `path`, `lastSubmitted`, `lastDownloaded`, `isPending`, `isSitemapsIndex`, `type`, `errors`, `warnings` и `contents[{type,submitted,indexed}]`. Устаревший счётчик `indexed` помечается (`indexed_deprecated`, `sitemap_indexed_count_deprecated`), а дочерние URL индекса сообщаются как нераскрытые (`sitemap_index_children_not_exposed`), а не угадываются. Отправка и удаление остаются `WRITE_DISABLED`, потому что движок подписывает `webmasters.readonly`.
- **Фильтры запросов GSC.** `gsc query` получает `--type`, повторяемый `--filter dimension:operator:expression`, повторяемый `--filter-list dimension:expr1,expr2`, `--data-state`, `--aggregation`, `--search-appearance` и `--branded`. Ответы добавляют `responseAggregationType` и `metadata` о неполных данных (`firstIncompleteDate`/`firstIncompleteHour`), когда Google их возвращает. Пределы не изменились: 25 тыс. строк на страницу и 50 тыс. строк/день/сайт/тип. Богатые селекторы доступны только в CLI.
- **Исправление событий Яндекса.** `search-urls/events/history` читал список `events`, но API возвращает `indicators{APPEARED_IN_SEARCH,REMOVED_FROM_SEARCH}[{date,value}]`, поэтому каждый вызов сообщал `empty_history` и терял реальные данные. Теперь ряды appeared/removed объединяются по дате. Живое окно 2026-10-02 вернуло 57 appeared / 0 removed. Если endpoint сбрасывает соединение на окне дат, клиент повторяет запрос без окна, фильтрует локально и предупреждает `client_side_date_filter`.
- **Глубина чтения Яндекса.** `yandex indexing` принимает `--date-from/--date-to` и объединяет ряды событий с HTTP-рядами индексации. `yandex samples --kind indexing|events [--limit] [--offset]` листает endpoint примеров с честными `total`/`truncated` (100 на страницу). `yandex sitemaps [--id] [--parent-id] [--limit] [--from]` читает списки и детали карт (`sitemap_id`, `sitemap_url`, `last_access_date`, `errors_count`, `urls_count`, `children_count`, `sources[]`, `sitemap_type`); добавление/удаление не реализовано. `yandex history --kind sqi|in-search|queries|query [--query-id]` читает SQI, страницы в поиске, все запросы и ряды одного запроса. `yandex queue [--id]` читает задачи переобхода с `count` провайдера.
- **Переобход Яндекса подключён.** `yandex recrawl` планирует с `--allow-write` и применяет с `--confirm TOKEN`: один `POST` на URL, с ограничением по `quota_remainder`, обрабатывая `202` (`task_id`, `quota_remainder`), `409 URL_ALREADY_ADDED` как `already_queued` и `429 QUOTA_EXCEEDED` с остатком URL в `not_attempted`. Пакетного endpoint нет.
- **Глубина чтения Bing.** `bing pages` (`GetPageStats`), `bing traffic` (`GetRankAndTrafficStats`, ежедневно), `bing crawl` (`GetCrawlStats`, шестимесячные дневные корзины), `bing urlinfo --url URL|domain:HOST` (`GetUrlInfo`), `bing children --url ... [--page] [--pages]` (`GetChildrenUrlInfo`, read POST, не более 10 страниц), `bing users` (`GetSiteRoles`, только чтение), `bing sites` (`GetUserSites`) и `bing joins --query|--page` (`GetQueryPageStats`, `GetPageQueryStats`, `GetQueryPageDetailStats`). Сентинел `Date(-62135596800000)` отображается в `null` и помечается `never_crawled`; `TotalChildUrlCount` хранится отдельным полем.
- **Честные пустые ответы.** Статистика и связки добавляют `no_rows_for_window`, `crawl` всегда добавляет `crawl_stats_six_month_window`, а поиски и списки — `provider_returned_no_rows`. Ноль строк больше не выдаётся за «ноль показов».
- **Органическая Метрика.** Новая группа только для чтения `metrika`: `pages`, `goals`, `queries`, `devices`, `countries`, `engagement` и `bytime`. SEO-коллектор применяет `filters=ym:s:lastTrafficSource=='organic'`; `stats` и `report weekly` показывают `organic_visits`/`organic_users`, а весь трафик явно как `all_visits`/`all_users`. `metrika pages` возвращает органические страницы входа с визитами/пользователями, отказами, средней длительностью, глубиной и просмотрами. `metrika goals` опрашивает настроенные id целей, при желании по `page` или `source`; пустой список — честное предупреждение, а больше пяти целей обрезаются по лимиту Метрики в 20 метрик. Поля сэмплирования (`sample_share`, `sample_size`, `sample_space`, `data_lag`, `contains_sensitive_data`, `total_rows_rounded`) переносятся в meta и limitations; точным считается только `sampled=false`.
- **Глубина CrUX и PSI.** `cwv audits --url ABS [--strategy mobile|desktop] [--category ...]` возвращает до 100 ограниченных аудитов Lighthouse (`id`, `title`, `score`, `display_value`, описание без HTML, `details_type`, экономия, `items_count`). `runtimeError`, CAPTCHA и редиректы становятся предупреждениями/ограничениями, а не чистым запуском. `cwv collect` получает повторяемый `--category`. `cwv history (--url ABS | --origin ABS) [--device] [--weeks 1..40]` читает недельные ряды p75 CrUX с честными пропусками и усечением. `collectionPeriod.firstDate/lastDate` теперь определяет `data_age_days`; двухдневная эвристика остаётся только запасной с `crux_period_missing`, а `urlNormalizationDetails` даёт `crux_url_normalized`.
- **Правила IndexNow.** Ключ должен соответствовать `[A-Za-z0-9-]{8,128}` и проверяется до планирования. Каталог `keyLocation` на том же хосте обязателен. Ответы: `200 accepted`, `202 accepted_pending`, `400` формат, `403 AUTH_INVALID` с точным ожидаемым URL ключа, `422` несоответствие хоста/ключа и `429` квота/спам. Ключ никогда не выводится.
- **Поверхность и схема.** 24 команды CLI верхнего уровня (17 групп и 7 команд, добавлена `metrika`), 12 инструментов MCP (10 класса чтения: 7 чистых только для чтения и 3 инструмента, сохраняющих локальное состояние; 2 записи с воротами), 3 ресурса и 3 промпта без изменений, схема версии 4 без миграции. `seo_indexing_triage` получает необязательный вход `url` и возвращает одну инспекцию GSC; `schemas/tools.json` перегенерирован из-за этого входа. Чтение карт GSC и богатые селекторы поиска доступны только в CLI, поэтому тринадцатый инструмент не добавляется.

## Приложение 0.9.0

Выпущено 2026-11-17. Оно добавляет экран Diagnostics только для чтения поверх движка `0.11.0`,
включает `lv24-seo 0.11.0` и поднимает `MIN_ENGINE_VERSION` до `0.11.0`, поэтому установленный
движок `0.10.x` считается несовместимым. Новой поверхности записи нет.

Что изменилось:

- **Экран Diagnostics только для чтения.** В боковом меню появляется **Diagnostics** (`/diagnostics`) с пятью вкладками: Google (`gsc_inspect`, `gsc_sitemaps`), Yandex (`yandex_indexing`, `yandex_sitemaps`, `yandex_queue`), Bing (`bing_pages`, `bing_traffic`, `bing_crawl`, `bing_urlinfo`, `bing_joins`), Metrika (`metrika_pages`, `metrika_goals`, `metrika_devices`, `metrika_countries`, `metrika_engagement`, `metrika_bytime`) и Core Web Vitals (`cwv_audits`, `cwv_history`). Каждая команда идёт через фиксированный белый список `cli_run`; на экране нет кнопок записи, токенов подтверждения и пути `--allow-write`.
- **Вкладка Google.** `gsc_inspect` проверяет ровно один абсолютный URL и показывает вердикт, состояние покрытия, состояние robots/индексации, последний обход, состояние загрузки, канонические URL Google/пользователя, `crawledAs`, ссылающиеся URL, проблемы расширенных результатов и ссылку на проверку. `gsc_sitemaps` перечисляет отправленные карты с типом, признаком индекса, ошибками, предупреждениями и числом отправленных элементов. Устаревший счётчик `indexed` помечен; дочерние URL индекса не раскрываются.
- **Вкладка Yandex.** `yandex_indexing` показывает события appeared/removed и HTTP-корзины индексации за окно дат. `yandex_sitemaps` перечисляет id карт, число URL/ошибок и последний доступ. `yandex_queue` перечисляет задачи переобхода с общим числом провайдера. Сброс провайдера или пустой ответ показывается как `client_side_date_filter` / `provider_returned_no_rows`, а не как нулевые данные.
- **Вкладка Bing.** `bing_pages`, `bing_traffic`, `bing_crawl`, `bing_urlinfo` и `bing_joins` показывают статистику страниц, дневные клики/показы, шестимесячные корзины обхода, детали индексации/обхода URL и связки запрос/страница. Пустая статистика отображает `no_rows_for_window`; поиски — `provider_returned_no_rows`. Сентинел `Date(-62135596800000)` показывается как «never», а не 0001.
- **Вкладка Metrika.** `metrika_pages`, `metrika_goals`, `metrika_devices`, `metrika_countries`, `metrika_engagement` и `metrika_bytime` работают только с органическим трафиком. Вкладка показывает `meta.organic_only`, поля сэмплирования и все ограничения.
- **Вкладка Core Web Vitals.** `cwv_audits` перечисляет ограниченные аудиты Lighthouse с оценкой, отображаемым значением и экономией; `cwv_history` перечисляет недельные ряды p75 CrUX с периодами сбора. URL с малым трафиком показывает явное пустое состояние `low_traffic`, а не пустую таблицу.
- **Честное оформление отчётов.** Каждая вкладка отображает `total`, `truncated`, `data_age_days` и `limitations` движка (или сообщает, что ограничений нет). Пустые ответы провайдера — явные состояния, а не нули. Панели не повторяют чтение автоматически.
- **Усиление моста.** Rust-мост добавляет 18 id команд в белый список и отклоняет до запуска движка: флаги записи (`allowWrite`, `confirm`) и токены на каждой диагностической команде; неизвестные значения `group`, `strategy`, `device` или `category`; аргументы, принадлежащие другой команде; и переопределение `--site` для чтения Bing (цель остаётся `providers.bing.site`). Webview не может передать исполняемый файл, shell-строку или произвольный флаг. Диагностические команды требуют конфигурацию и не отменяемы, как другие короткие чтения.
- **Движок 0.11.0 и контракты.** `MIN_ENGINE_VERSION` равен `0.11.0`; установленный sidecar `0.10.x` сообщается как несовместимый вместо ошибки `CLI_INVALID_JSON`. Встроенный onedir sidecar — `lv24-seo 0.11.0`. Контракты (`config.schema.json`, фикстуры CLI включая `stats`) перегенерированы из движка `0.11.0`. Отправка URL в Bing, отправка карты в Bing и IndexNow сохраняют свои двухфазные ворота; отправка карты GSC и удаление карты Bing остаются `WRITE_DISABLED`.

Известные ограничения 0.9.0:

- Цели Метрики показываются только как итоги; приложение не раскрывает необязательный селектор движка `--dimension page|source`.
- История CWV «all devices» опускает фильтр устройства, а не изобретает объединённую строку.
- Чтение Bing использует `providers.bing.site`; в приложении нет переопределения `--site`.
- У Bing Site Scan по-прежнему нет публичного API: карточка Integrations только открывает официальную страницу и не может импортировать отчёт.
- Движок старше `0.11.0` сообщается как несовместимый. Обновите движок или установите встроенный sidecar.
- Панели Diagnostics не повторяют запрос автоматически; сбой показывает ошибку движка и ручной повтор.
- Экран по замыслу только для чтения: он не добавляет действий переобхода, отправки карты или URL.

## Движок 0.10.0

Выпущен 2026-11-17. Он превращает отправку URL в Bing в настоящую защищённую запись и добавляет
представления только для чтения: квоту, фиды sitemap и проблемы обхода. В CLI теперь 23 команды
верхнего уровня; поверхность MCP остаётся в 12 инструментов, схема SQLite — версия 4.

Что изменилось:

- **Отправка URL в Bing.** `bing submit [--url ABS …] [--from-sitemap] [--sitemap-url ABS] [--site URL] [--allow-write] [--confirm TOKEN]` отправляет URL через Bing Webmaster `SubmitUrlbatch`. `--url` можно повторять и объединять с `--from-sitemap`; `<urlset>` читается напрямую, `<sitemapindex>` ограничен корнем плюс пятью дочерними sitemap и 10 000 URL, явные URL дедуплицируются первыми, URL вне сайта пропускаются, а `meta.truncated`, `meta.total` и `meta.limitations` сообщают о каждом пределе или пропуске. План показывает число URL, число пакетов по 500 URL и текущий остаток квоты в `meta.quota`; он не обращается к endpoint записи. Применение заново загружает sitemap и аннулирует токен с `CONFIRM_REQUIRED`, если набор URL изменился.
- **Пакеты по 500 URL и честный статус.** `SubmitUrlbatch` вызывается явными пакетами по 500 URL после клиентской проверки квоты по дневному и месячному окнам. Успех пакета — `200 {"d": null}` без статуса по каждому URL, поэтому результат говорит `status: accepted` и `accepted`, а не «проиндексировано»; сообщаются `duplicates_removed`, `batches`, `batch_size` и `quota_after`. Bing не документирует идемпотентность отправки, и повторный URL может израсходовать квоту (`submit_idempotency_undocumented`), но журнал записи SQLite всё равно возвращает для повторного токена `status: skipped` с `reason: duplicate`. Отсутствующий `providers.bing.site` — `CONFIG_INVALID`, отсутствующий `bing_api_key` — `AUTH_REQUIRED`, и ключ никогда не попадает в ошибку.
- **Квота Bing.** `bing quota` читает `GetUrlSubmissionQuota`. `DailyQuota` и `MonthlyQuota` — это **остаток** отправок, а не всего: строки содержат `daily_remaining` и `monthly_remaining` плюс объект провайдера в `raw`, а значения использовано/всего никогда не вычисляются. Ограничения `quota_monthly_can_bind_first` и `quota_monthly_reset_undocumented` говорят, что месячное окно может закончиться раньше дневного и что Bing не публикует расписание месячного сброса.
- **Фиды sitemap Bing.** `bing sitemaps [--details FEED_URL]` читает `GetFeeds` и отображает URL, тип, статус, дату отправки, последний обход, число URL, размер файла и сжатие. `LastCrawled` (с запасным `Submitted`) ограничивает `data_age_days`; `Status` — свободная строка провайдера, например `Success`, а не статус обхода или индексации. Bing не отдаёт ошибки по отдельным URL и постраничность, поэтому результат несёт `no_per_url_sitemap_errors` и `sitemap_status_is_not_crawl_status`. `--details` читает `GetFeedDetails` для дочерних элементов sitemap-индекса; это опция, а не отдельная команда.
- **Проблемы обхода Bing.** `bing issues` читает `GetCrawlIssues` и возвращает URL, HTTP-код, входящие ссылки и битовую маску `Issues`, декодированную в метки (`1=301`, `2=302`, `4=4xx`, `8=5xx`, `16=robots`, `32=malware`, `64=important_robots`, `128=dns`, `256=timeout`). Неизвестные биты сообщаются через `unknown_crawl_issue_bits`, а не угадываются. У фида нет даты, поэтому `data_age_days` равен `0`, и нет серьёзности.
- **Сопоставление ошибок Bing.** Bing возвращает ошибки аутентификации как HTTP 400 с числовым `ErrorCode`, а не 401/403. Адаптер сопоставляет `3` с `AUTH_INVALID`, `14` с `PROPERTY_NOT_FOUND`, `7` с `INVALID_INPUT`, `4/5` с `QUOTA_EXCEEDED`, сохраняет 401/403/404/429/5xx как запасные варианты и никогда не повторяет сообщение провайдера или API-ключ.

Отправка URL, квота, sitemap и проблемы Bing доступны только в CLI и приложении: тринадцатый инструмент MCP не добавляется, а `seo_sitemap_submit` по-прежнему отправляет sitemap, а не пакет URL.

Адаптер подписывает RS256 JWT (`iss`, `scope=webmasters.readonly`, `aud`, `iat`, `exp`), обменивает его в `token_uri` ключа по JWT-bearer grant и обновляет за 60 секунд до истечения; обычный токен сохраняет историческое поведение `Authorization: Bearer` и не обновляется. `properties` сообщает `token_source: service_account_file|secret|missing` и помечает GSC готовым; `doctor` добавляет некритичную проверку `gsc_auth`. Ни один из них не печатает JSON или приватный ключ, а `auth status` по-прежнему смотрит только keychain, окружение и файловые секреты. - **Недеструктивное восстановление.** `backup restore --file ABS --to ABS_DIR` распаковывает архив в новый каталог и никогда не трогает текущую рабочую область. Архив перепроверяется точно как при плане на месте (манифест, набор и имена членов, размеры, каждый SHA-256). Цель должна быть абсолютным путём, которого не существует, с существующим родителем; существующая, непустая или символическая цель — `INVALID_INPUT` и никогда не объединяется и не перезаписывается. Абсолютные пути, `..`, обратные слэши и символические ссылки внутри архива отклоняются до распаковки, база проходит `PRAGMA quick_check` до и после перемещения на место, а staging-каталог удаляется. Сгенерированные задания содержат абсолютный путь `--config` и запускаются из каталога конфигурации. `schedule status` только читает и сообщает `installed|outdated|partial|missing|unknown`, ожидаемые пути и `exists`/`matches` по артефактам; `unknown` означает, что планировщик хоста не удалось проверить, и `matches` тогда `null`. `schedule uninstall` по умолчанию только планирует, а с `--allow-write` удаляет ровно свой управляемый блок cron, два unit-файла `<job>.service`/`<job>.timer` или именованную задачу; повторный запуск — no-op (`removed: false`, `state: missing`), а чужие строки и задачи никогда не трогаются. - **Двухфазное восстановление.** `backup restore --file ABS --config ABS` проверяет архив и возвращает план с хешами архива и манифеста, целевым каталогом конфигурации и данных, текущим и архивным хешами базы, действием с конфигурацией (`create`, `replace` или `write_alongside`) и `confirm_token` на 300 секунд. Для применения нужны `--allow-write` и токен; один `--allow-write` только планирует, токен без него — `WRITE_DISABLED`, а изменённый архив, другая рабочая область, истёкший токен или повтор дают `CONFIRM_REQUIRED`. Перед заменой текущая база копируется в `<db>.pre-restore-<utc>` (а конфигурация — в `seo.toml.pre-restore-<utc>`, если она заменяется), каждый хеш члена перепроверяется, восстановленная база проходит `PRAGMA quick_check`, файлы заменяются атомарно. Конфигурация, не прошедшая валидацию, записывается рядом как `seo.toml.restored-<utc>`.
- **Портфель нескольких сайтов.** `portfolio list --root ABS [--limit 1..50]` сканирует до трёх уровней ниже абсолютного каталога в поисках `seo.toml`, пропуская скрытые, `node_modules`, `__pycache__`, `venv` и символические каталоги, и возвращает строку на сайт: путь конфигурации, имя, свойство, базовый URL, каталог данных, наличие базы, запуски обхода, снимки отчётов, счётчики проблем и последнюю активность. Он не вызывает провайдера, не читает токен и ничего не пишет. Сломанная конфигурация или недоступная база становятся `error` этого сайта, остальные продолжают сканироваться; скан ограничен 50 сайтами и сообщает реальный `total` с `truncated: true`.
- **Схема v4 и события индексирования.** Миграция v4 добавляет `indexing_events` с ключом `(provider, property_id, url, event, event_date)`. `yandex indexing` и вызов MCP `yandex_indexing_state` сохраняют события по URL, когда есть хранилище: повтор обновляет `last_seen` без дублирования, `first_seen` неизменяем, `meta.indexing_events` сообщает `new`, `existing`, `skipped` и `truncated`, а сбои хранилища становятся предупреждениями, а не неудачным чтением провайдера. Недельный дайджест теперь читает эти события, поэтому доказательства `indexing_event` больше не зависят от переданных вызывающим строк.
- **Core Web Vitals по шаблону.** Когда в хранилище есть полевые строки CrUX/PSI для сравниваемых окон, `report weekly` и `seo_weekly_report` добавляют раздел `cwv` с группировкой по нормализованному шаблону URL (`/blog/{id}`) и устройству (`phone`, `desktop`, `tablet`). Показывается не более пяти шаблонов, сначала регрессировавшие, с p75 по каждой метрике, предыдущим p75, дельтой, флагом регрессии и `poor_metrics`. Регрессия — рост p75 не менее чем на 5% (выше 0,01 для CLS), а p75 шаблона — худший p75 страницы в группе, а не среднее по сайту. Агрегаты origin, лабораторные/PSI-оценки и строки без URL или известного устройства никогда не объединяются; они сообщаются через `cwv_template_missing`, `cwv_device_missing`, `cwv_lab_ignored` и `cwv_values_ignored`.
- **Поверхность и схема.** 21 команда CLI верхнего уровня (14 групп и 7 команд, добавлены `portfolio` и `backup restore`), 12 инструментов MCP (10 класса чтения: 7 чистых только для чтения и 3 инструмента, сохраняющих локальное состояние; 2 записи с воротами всё ещё возвращают `WRITE_DISABLED`), 3 ресурса и 3 промпта без изменений. ## Движок 0.5.3

Выпущен 2026-11-16. Он делает записи агентов двухфазными, уводит обход с event loop MCP,
добавляет код выхода `--strict` для CI и заменяет общие сбои хранилища типизированными кодами. Без
миграции схемы, без новых CLI-команд и MCP-инструментов: поверхность остаётся в одиннадцать
инструментов, меняются входы, коды выхода и коды ошибок.

Что изменилось:

- **Двухфазные записи MCP.** `seo_recrawl_request` и `seo_sitemap_submit` принимают `allow_write` (по умолчанию `false`), `plan_hash` и `confirm_token`. Вызов без токена — это dry run, возвращающий план, его хеш и токен на 300 секунд; применение должно повторить хеш и токен. Несовпадающий хеш даёт `CONFIRM_REQUIRED`, повтор возвращает `status: skipped` с `reason: duplicate`, а ошибка провайдера освобождает заявку, поэтому повтор разрешён. `LV24_SEO_WRITE_SECRET` обязателен; пустой секрет — это `WRITE_DISABLED`. В поставляемом `SeoService` по-прежнему нет адаптера записи для переобхода или карты сайта, поэтому оба инструмента возвращают `WRITE_DISABLED` даже с `allow_write=true`: контракт есть, вызова провайдера нет.
- **Обход вне event loop.** `seo_crawl_site` идёт в рабочем потоке с собственным короткоживущим хранилищем и жёстким бюджетом 600 секунд. После бюджета клиент получает повторяемый `UPSTREAM_UNAVAILABLE` с предложением меньшего `max_urls`; поток завершается в фоне, а сервер продолжает отвечать другим инструментам. Остальные инструменты остаются сериализованными на owner loop.
- **`--strict` и код 5.** `stats`, `gsc query`, `yandex queries`, `yandex indexing`, `crawl`, `report weekly` и `report diff` принимают `--strict`. `meta.strict` выставляется всегда; усечённый ответ остаётся `ok: true`, но выходит с `5`, а `meta.limitations` объясняет, чего не хватает. Без флага усечение по-прежнему выходит с `0`. `report diff --markdown` соблюдает тот же код.
- **Журнал записи следует за `--config`.** Применение записи открывает журнал идемпотентности из каталога данных выбранной рабочей области, поэтому `--config /srv/site/seo.toml` записывает заявку в `/srv/site/data`, даже если оболочка в другом месте. Раньше журнал разрешался от рабочего каталога, что молча отключало защиту от повтора.
- **Типизированные ошибки хранилища.** `STORE_LOCKED` (повторяемая), `STORE_CORRUPT` (с `detail.backup_path`) и `STORE_UNAVAILABLE` заменяют общий конверт `INTERNAL`. Повреждённый файл копируется рядом с собой до любых других действий; оригинал никогда не перемещается и не удаляется. Все три кода выходят с `1`, как `INTERNAL`.
- **Честные данные провайдеров.** Усечённый результат GSC не содержит `total` вместо точного числа рядом с `truncated: true`, а `data_age_days` не меньше документированной задержки 3 дня. `limit` Metrika — это размер страницы: клиент листает `offset` до 10 000 строк и 100 страниц, помечает полную страницу без `total_rows` как усечённую и никогда не листает агрегатный вызов. Bing берёт `data_age_days` из даты самой новой строки вместо жёсткого нуля. Загруженный хост Yandex с пустой историей возвращает `total: 0` с `empty_history`, а не `degraded_host`, и обычный `count` Webmaster больше не принимается за общий итог.
- **Область карты сайта.** `<loc>` вне собственных origin карты сайта (origin стартовой карты плюс конечный origin каждого прочитанного документа) отбрасывается и один раз сообщается как `off_origin_loc`, поэтому индекс никогда не уведёт читателя на другой сайт.
- **`doctor` считает объявленный каталог данных критичным.** Когда конфиг или `LV24_SEO_DATA_DIR` задаёт каталог, отсутствующий или непригодный каталог валит проверку; `meta.data_dir_declared` сообщает, какой это случай.
- **Мелкие исправления.** Crontab с незавершённым управляемым блоком чинится консервативно: удаляются только строки, похожие на записи lv24-seo, а предупреждение просит оператора проверить `crontab -l`. Обход соблюдает один `429` `Retry-After`, а не считает троттлинг ответом страницы.

## Приложение 0.2.3

Выпущено 2026-11-16. Оно переносит загрузку обновления в Rust, делает путь конфигурации возможностью, одобряемой
диалогом, отклоняет сетевые пути до открытия и исправляет состояние UI, которое могло неверно сообщать о сохранении
или рабочей области. Оно включает `lv24-seo 0.5.3` и оставляет `MIN_ENGINE_VERSION` на `0.5.2`, поэтому установленный
движок `0.5.2` по-прежнему принимается.

Что изменилось:

- **Обновлятор перенесён в Rust.** В списке возможностей webview только `updater:allow-check`. `update_install` заново проверяет endpoint, отказывается от версии, отличной от объявленной панелью (`UPDATE_VERSION_MISMATCH`), скачивает, проверяет подпись и запускает установщик; прогресс приходит как `update://progress`. `update_cancel` отбрасывает загрузку до запуска установщика и возвращает `UPDATE_CANCELLED`; после начала установки он возвращает `false`, и панель остаётся как есть.
- **Путь конфигурации, одобренный диалогом.** `pick_config` записывает файл, возвращённый нативным диалогом; `settings_set` принимает только активный или одобренный путь и отклоняет остальное с `PATH_NOT_APPROVED`. UNC-шара, устройство `\\?\` или `\\.\` в `storage.data_dir` отклоняется с `INVALID_PATH` и `detail.reason: network_or_device_path` до разрешения.
- **Редактирование и таймауты.** stderr движка редактируется до того, как попасть в webview, лог или диагностический пакет, причём до усечения 300-символьного превью. Ошибка TOML-парсера тоже редактируется. Вспомогательная задача сверх бюджета падает с `PATH_TIMEOUT`, а не подвешивает экран.
- **Рабочая область и состояние UI.** `shell_status` сообщает `configExists`; перемещённый или удалённый конфиг показывает баннер отсутствующей рабочей области с **Choose config** вместо общей ошибки статистики. У блоков провайдеров есть явный переключатель включения — единственный писатель `providers.<id>.present`. Валидация трёхзначна (`valid`, `invalid`, `skipped`), поэтому двойной клик или переключение рабочей области больше не сообщают о валидном черновике как о невалидном. Skip-link сохраняет hash-маршрут, а маршрутный error boundary локализует сбой рендера и предлагает перезагрузку.
- **Релизный конвейер.** CI на pull request запускает тесты релизных скриптов; матрица Rust включает Intel macOS runner, который использует релиз; Rust закреплён на `1.95.0`. `latest.json` валидируется по `contracts/latest.schema.json` до создания черновика. Один протестированный список управляет файлом контрольных сумм и списком загрузки, а Windows portable ZIP поставляется с sidecar `.sha256`, который релизный гейт пересчитывает и сравнивает.

## Движок 0.5.2

Это bugfix-релиз линии 0.5.x. Он закрывает блокеры, найденные после 0.5.1: относительный
`storage.data_dir` в `seo.toml` следовал за рабочим каталогом оболочки, CLI собирал write-gate без
журнала идемпотентности, ошибки загрузки sitemap эхом возвращали URL с query-токенами, а GSC
заявлял полное покрытие, когда последняя страница ровно заполняла лимит строк.

Без миграции схемы и без новых CLI-команд или MCP-инструментов. JSON-конверт сохраняет прежние
ключи; `doctor` добавляет аддитивные поля `meta.data_dir` / `meta.data_dir_source` и может нести
предупреждение. Существующие хранилища открываются без изменений, а конфиги с абсолютным
`data_dir` работают как раньше.

Что изменилось:

- **Привязка data-dir.** Относительный `storage.data_dir` из `seo.toml` теперь разрешается
  относительно каталога этого файла, поэтому `lv24-seo --config /srv/site/seo.toml` использует
  `/srv/site/data` из любого рабочего каталога. `init` создаёт `<config dir>/data` и пишет
  `data_dir = "./data"`. Встроенное значение по умолчанию (без блока `[storage]`) и
  `LV24_SEO_DATA_DIR` намеренно остаются привязанными к процессу. `doctor --json` сообщает
  `meta.data_dir` и `meta.data_dir_source` (`config` или `working directory`), а
  `config show --json` показывает эффективный путь.
- **Абсолютные пути планировщика.** `resolve_config_path` всегда возвращает абсолютный
  нормализованный путь. `schedule install` и `schedule print` встраивают абсолютный аргумент
  `--config` и используют родительский каталог конфига как рабочий каталог, поэтому задание
  запускает тот же конфиг из любого каталога планировщика.
- **Повторобезопасные записи CLI.** Команда записи с `--confirm` открывает SQLite-журнал рабочей
  области и передаёт его в `WriteGate`. Повторный токен возвращает `status: skipped` с
  `reason: duplicate`, и провайдер вызывается ровно один раз. Dry run не открывает журнал и не
  создаёт базу. Без инициализированной рабочей области команда всё равно работает, но конверт
  предупреждает, что защита от повтора отключена на пять минут жизни токена.
- **Маскирование URL в предупреждениях sitemap.** Неудачная загрузка sitemap сообщает только тип
  исключения (`HTTPError`, `TimeoutError`, …), но не URL и не query-строку. Сбой остаётся
  видимым и машиночитаемым, но `?key=…` не попадает в предупреждения, `limitations[]` или
  MCP-полезную нагрузку.
- **Честность точного лимита GSC.** Последняя страница GSC, которая ровно заполняет лимит в
  50 000 строк, помечается `truncated: true` с `rows_cap_50000`; меньший лимит вызывающего даёт
  предупреждение с его значением. Нулевой лимит считается лимитом, а не пустым результатом.
  Полная страница не доказывает, что за лимитом нет строк.
- **Опциональное маскирующее логирование.** `LV24_SEO_LOG_LEVEL` устанавливает redacting-handler
  ровно в двух точках входа: callback CLI и `lv24-seo mcp serve`. Если переменная не задана,
  конфигурация логирования вызывающего не меняется. Вывод — одна JSON-строка на запись, когда
  stderr не терминал (pipe, лог планировщика, MCP-хост), и обычная строка в терминале.
  MCP-транспорт пишет только в stderr; stdout остаётся протоколом.
- **Мелкие исправления.** Pending-заявка записи после падения по-прежнему не имеет TTL; удаление
  `data/seo.sqlite3` сбрасывает журнал; `doctor` не падает на относительном data-dir.

| `mypy src` | Чисто |
| MCP registry `--check` | Чисто (поверхность не менялась) |

Известные ограничения 0.5.2:

- Конфиг, открытый через symlink, привязывает data-dir рядом со ссылкой, а не с целью: symlinks
  намеренно сохраняются. `LV24_SEO_DATA_DIR` остаётся process-scoped переопределением.
- Pending-заявка записи после падения не имеет TTL и считается выполняющейся, пока оператор её не
  освободит. Это намеренно: ложный повтор может дублировать запись провайдера.
- Без data-dir защиты от повтора нет; токен остаётся валидным все пять минут.
- Сайт ровно с 50 000 строк GSC и без строк за лимитом тоже помечается truncated. Это намеренно:
  полная страница не доказывает отсутствие следующей строки.
- Логирование остаётся опциональным. Правила редактирования покрывают чувствительные ключи,
  известные префиксы токенов и длинные непрозрачные значения, но не каждый формат секрета
  конкретного провайдера.

### Очистка sidecar перед обновлением

Sidecar движка лежит внутри установленного каталога ресурсов, поэтому запущенный процесс
`lv24-seo` держит файл заблокированным и NSIS-установщик не может его заменить. Перед запуском
установщика оболочка вызывает `prepare_update`, который останавливает **только те PID движка,
которые зарегистрировал этот экземпляр приложения** при их запуске. Ничего не ищется по имени
образа, поэтому другая установленная копия, portable-сборка, запущенный в терминале `lv24-seo`
или посторонний процесс не затрагиваются. Короткое ожидание (2 с) подтверждает завершение.

Если очистка не удалась, установка блокируется с `UPDATE_ENGINE_BUSY`, а не запускает установщик,
который сломается на середине. Ошибка повторяемая: закройте запуск, удерживающий sidecar, и
нажмите кнопку снова.

### Секреты и конфигурация

- Yandex Metrika сохраняет собственный auth-провайдер (`metrika`, `yandex_metrika_token`) в списке
  провайдеров, бейдже Settings, окне секретов и подписях en/ru/zh. Он никогда не берёт токен
  Webmaster.
- Приложение и CLI используют **одну запись OS keychain на провайдера** (сервис `lv24-seo`).
  Токен, введённый через `lv24-seo auth set --provider <p> --stdin` в терминале, появляется в
  `auth status` приложения без повторного ввода, а токен из приложения виден CLI.
- Токен из `LV24_SEO_*` показывается в UI как **read-only**: приложение не может удалить переменную
  окружения и говорит об этом, а не предлагает кнопку удаления, которая ничего не делает.
  `auth logout` с `deleted: false` показывается честно.
- Состояние workspace, отчёта, doctor и секретов очищается при смене workspace или переходе движка
  в offline. Действия, которые не могут работать, отключаются, а не падают по клику. Каталоги
  сообщений en/ru/zh согласованы; отсутствующий ключ — ошибка теста.
- Запись конфигурации и настроек атомарна **и fsynced** (файл и родительский каталог). Временные
  черновики и резервные копии имеют режим `0600`; чтение конфига ограничено 8 MiB; настройки
  загружаются по полям; зарезервированные имена Windows и завершающие точки/пробелы отклоняются
  в каждом компоненте пути. stderr валидации конфигурации редактируется до попадания в UI или лог.

| Пакет | Обновление в приложении | Что происходит |

| macOS `.app` | Да | Скачивает подписанный `.app.tar.gz`, заменяет приложение, перезапускает |
| Linux AppImage | Да | Скачивает подписанный AppImage, заменяет его, перезапускает |

| Неизвестный пакет | Нет | Settings ведёт на страницу релиза |

Manual-only — намеренно. Пакет deb или rpm принадлежит базе пакетов; MSI этим проектом не
производится, и NSIS-пакет обновления не может его заменить; portable ZIP не имеет установщика,
который можно заменить, и может лежать на съёмном носителе. Приложение сообщает тип установленного
пакета и отключает встроенный установщик для таких случаев. Оно не делает вид, что ручной пакет
был обновлён.

Путь Windows NSIS теперь проверен end-to-end девять раз: `0.2.0 → 0.2.1`, `0.2.1 → 0.2.2`,
`0.2.2 → 0.2.3`, `0.2.3 → 0.3.0`, `0.3.0 → 0.4.0`, `0.4.0 → 0.5.0`, `0.5.0 → 0.6.0`, `0.6.0 → 0.7.0`
и `0.7.0 → 0.8.0`. В девятом запуске установленная сборка `0.7.0` обновилась через Rust-обновлятор,
скачала и проверила подписанный пакет, установила его, перезапустилась и сообщила **Desktop 0.8.0**
с **Engine 0.10.0** и готовым движком; загрузились карточки отправки URL, sitemap, проблем обхода и
квоты Bing. `0.8.0 → 0.9.0` — следующий источник обновления. Любая установка `0.2.x` с обновлятором
может сразу перейти на `0.9.0`; у `0.1.0` нет обновлятора, нужна одна ручная установка.

Обновление `0.2.1 → 0.2.2` выполняет старый обновлятор `0.2.1`, в котором нет новой очистки
отслеживаемых PID. Если во время первого обновления активен sidecar, повторите после его выхода
или установите `0.2.2` вручную. `0.2.2 → 0.2.3` и последующие обновления используют очистку
отслеживаемых PID и блокируются с `UPDATE_ENGINE_BUSY`, если отслеживаемый sidecar не удаётся остановить.

## Релизный конвейер

Workflow приложения ручной и owner-gated. У него нет триггеров push, pull-request или tag. Владелец
запускает **Actions → Desktop build → Run workflow** и подтверждает окружение `desktop-release`;
запуск не владельцем пропускается.

| Вход | Значение по умолчанию | Смысл |
|---|---|---|
| `engine_version` | `0.11.0` | Точная версия движка в sidecar |
| `signed` | `false` | Запросить подпись/нотаризацию ОС; в этом zero-spend репозитории не настроено |
| `publish` | `false` | Создать GitHub release после прохождения всей матрицы |
| `tag` | Пусто | Тег релиза `vX.Y.Z`; обязателен при `publish=true` |

Значение по умолчанию соответствует пину `0.7.0`. Релизный гейт отклоняет несоответствие
манифеста, если передана другая версия.

| Runner | Target | Пакеты |
|---|---|---|
| `windows-latest` | `x86_64-pc-windows-msvc` | NSIS |
| `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | AppImage, deb, rpm |
| `macos-15` | `aarch64-apple-darwin` | DMG + app |
| `macos-15-intel` | `x86_64-apple-darwin` | DMG + app |

Все runner'ы — стандартные GitHub-hosted. Не используются larger runner, платные минуты, платное
хранилище или платный сервис подписи. Артефакты сборки хранятся 7 дней; GitHub release — долговечный
канал распространения.

## Пин sidecar и контрольные суммы

Релизный sidecar — дерево PyInstaller **onedir**, собранное на соответствующем хосте; PyInstaller не
кросс-компилирует. Версии движка, Python, Pydantic, Typer и PyInstaller закреплены в
`scripts/cli-checksums.json`. `0.9.0` закрепляет движок `0.11.0` (выше `0.10.0`), Python `3.12`, Pydantic `2.14.3`,
Typer `0.29.0` и PyInstaller `6.22.3`.

Вывод PyInstaller onedir не байт-воспроизводим. Поэтому политика контрольных сумм разделена:

- **Локальная релизная сборка — строгая.** `scripts/verify-sidecar.mjs` должен совпасть с
  закоммиченными SHA-256 и размером; `--write` обновляет пин после ревью. `null` означает
  «ещё не проверено», а не «проверено».
- **CI-пересборка — rebuild-aware.** Job сборки запускает верификатор с `--no-hash` и записывает
  фактический SHA-256 в `release/sidecar-checksums-<target>.json`.
- **Релизный гейт — по отчётам.** Релизный job требует валидный отчёт для каждого отгружаемого
  target: совпадение имени target, `hashPolicy: "rebuild"`, `ok: true`, 64-hex хеш, положительный
  размер и точную версию движка.

Для `0.9.0` Windows x64 имеет проверенный локальный пин (`db02d1b3…`, 14 478 498 байт); sidecar для Linux и macOS пересобраны релизным
workflow с пройденными rebuild-aware отчётами, а их проверенные пины остаются `null`, пока локальная сборка
не будет проверена на этих хостах. Windows-пин `0.8.0`
не переносился, потому что исполняемый файл меняется вместе с движком. Отчёты контрольных сумм — доказательства CI, а не релизные артефакты.
`SHA256SUMS.txt` покрывает установщики, пакеты обновления, подписи и `latest.json`; исполняемый
файл sidecar находится внутри этих пакетов и отдельно не указан. При ручной установке сверяйте
скачанный артефакт с `SHA256SUMS.txt`.

```bash
node scripts/verify-sidecar.mjs \
  --root src-tauri/engine \
  --target x86_64-pc-windows-msvc \
  --engine-version 0.11.0
```

## `latest.json`, подпись и публикация

Подписи обновлений используют бесплатный ключ Ed25519/minisign, отдельный от подписи кода ОС.
Публичный ключ встроен в приложение; приватный — секрет репозитория, передаваемый только на шаг
сборки. Включён `requireSignedVersion`, поэтому объявленная версия привязана к подписанному пакету.
Обновление принимает только версию выше текущей, поэтому откатиться нельзя.

`scripts/stage-release-assets.mjs` выравнивает и нормализует имена пакетов и пишет метаданные
`updater-<platform>.json` для каждой платформы. `scripts/merge-latest-json.mjs` объединяет их в
`latest.json`:

- обязательные generic-ключи: `windows-x86_64`, `linux-x86_64`, `darwin-aarch64`,
  `darwin-x86_64`;
- bundle-алиасы, которые проверяет обновлятор: `windows-x86_64-nsis`, `linux-x86_64-appimage`,
  `darwin-aarch64-app`, `darwin-x86_64-app`;
- необязательные `linux-x86_64-deb` и `linux-x86_64-rpm` только если Tauri создал их подписи;
- каждый URL указывает под `releases/download/<tag>/`;
- каждая подпись сверяется с файлом `.sig` на диске;
- каждый упомянутый артефакт должен существовать;
- примечания берутся из `docs/releases/<version>.md`, если файл есть.

Релиз сначала создаётся как **draft**. Артефакты загружаются, пока он draft, `latest.json` —
последним, затем job публикует через `gh release edit --draft=false` и проверяет удалённые имена
артефактов. `releases/latest/download/latest.json` разрешается только на опубликованный релиз,
поэтому пользователи не видят частично загруженный манифест. Повторный запуск переиспользует
существующий draft, очищает его артефакты и отказывается перезаписывать опубликованный релиз.

## Закрепление версий

Версия приложения должна совпадать в `package.json`, `src-tauri/tauri.conf.json`,
`src-tauri/Cargo.toml`, Git-теге и заголовке релиза. Пин движка живёт в
`scripts/cli-checksums.json`; workflow передаёт `engine_version` явно, а релизный гейт требует
совпадения с манифестом.

`MIN_ENGINE_VERSION` в `src-tauri/src/commands.rs` в текущем исходнике равен `0.11.0`. Сборка `0.9.0`
включает движок `0.11.0`, поэтому минимум совпадает с движком сборки, а движок `0.10.x` считается
несовместимым. Оболочка
принимает движок не старше этой версии и помечает более старый как offline с уведомлением. Более
новый движок проходит гейт, но не является релизно-проверенным пином. Сборочная версия может
использовать `LV24_SEO_BIN` с другой версией; UI помечает его внешним и всё равно проверяет
минимум. Движок из `PATH` используется только при `LV24_SEO_ALLOW_PATH_ENGINE=1`.

## Откат

Автоматического отката нет. Откат — ручная установка более старого релиза.

| Сбой | Действие |
|---|---|
| Плохой установщик, но рабочее приложение | Выпустить исправленный патч; не перезаписывать артефакты под тем же тегом |
| Плохой `latest.json` | Выпустить исправленный патч; draft-гейт не даёт частичному манифесту стать видимым |
| Скомпрометированный ключ обновлений | Ротировать ключ, выпустить ручной релиз с новым публичным ключом; автообновление не переживает ротацию |
| Регрессия движка | Закрепить предыдущую версию движка, пересобрать и выпустить патч |
| Нужна старая сборка приложения | Установить вручную; обновлятор отказывается от понижения |

Не перемещайте и не переиспользуйте опубликованный тег. Держите артефакты предыдущего релиза
доступными для отката. Если endpoint нужно отключить, выпустите ручной релиз и задокументируйте это.

## Проверка загрузки

`SHA256SUMS.txt` покрывает каждый опубликованный артефакт. Проверьте файлы, которые собираетесь
устанавливать:

```bash
sha256sum -c SHA256SUMS.txt --ignore-missing
```

На macOS `shasum -a 256 -c SHA256SUMS.txt` доступен в базовой системе. В Windows сравните
`Get-FileHash <file> -Algorithm SHA256` с соответствующей строкой. Не запускайте файл, хеш которого
не совпадает.

По умолчанию пакеты ОС не подписаны (Windows, Linux) или подписаны ad-hoc (macOS). Подпись
обновления аутентифицирует обновления, а не первую ручную загрузку. Предупреждения SmartScreen и
Gatekeeper ожидаемы; сверьте контрольную сумму и используйте документированный путь
**More info → Run anyway** или **Open Anyway**. Не отключайте эти защиты глобально.

См. [Безопасность и приватность](/ru/security/) для доверия к обновлениям и [Архитектуру](/ru/architecture/) для раскладки sidecar.
