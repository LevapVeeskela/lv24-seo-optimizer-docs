# Релизы и обновления

Текущие релизы:

| Продукт | Версия | Дата | Примечания |
|---|---|---|---|
| Движок | `lv24-seo 0.9.0` | 2026-11-17 | Отправка sitemap в Bing, IndexNow из sitemap, необязательный `provider` в MCP, 22 команды CLI и 12 инструментов MCP |
| Приложение | `0.7.0` | 2026-11-17 | Панель индексации Bing, открытие Site Scan, посессионный секрет записи, движок 0.9.0 и `MIN_ENGINE_VERSION` 0.9.0 |

Версия приложения и версия движка независимы, но приложение закрепляет точный движок и отказывается работать с версией ниже минимальной. `0.7.0` включает `0.9.0` и требует минимум `0.9.0`, поэтому установленный движок `0.8.x` считается несовместимым.

## Движок 0.9.0

Выпущен 2026-11-17. Он превращает отправку sitemap в Bing в настоящую защищённую запись и позволяет
IndexNow читать список URL из sitemap проекта, а хост и ключ — из `seo.toml`. В CLI по-прежнему
22 команды верхнего уровня; поверхность MCP остаётся в 12 инструментов, схема SQLite — версия 4.

Что изменилось:

- **Отправка sitemap в Bing.** `sitemap submit --provider bing [--property SITE] [--url ABS] [--allow-write] [--confirm TOKEN]` отправляет sitemap сайта через актуальный JSON-endpoint Bing Webmaster `POST .../SubmitFeed` с `{"siteUrl": …, "feedUrl": …}`. Сайт берётся из `providers.bing.site` или `--property`, sitemap — из `--url` или `<project.base_url>/sitemap.xml`, ключ — из секрета `bing_api_key`; отсутствие сайта, base URL или ключа отклоняется до сетевого вызова. HTTP 401/403 дают `AUTH_INVALID`, 404 — `PROPERTY_NOT_FOUND`, 429 — `QUOTA_EXCEEDED`, 5xx — `UPSTREAM_UNAVAILABLE`, остальные 4xx — `INVALID_INPUT`; ключ никогда не попадает в ошибку. `--provider` по умолчанию `gsc`, поэтому старые скрипты сохраняют план GSC.
- **Двухфазная запись Bing.** И план, и применение требуют `--allow-write` и `LV24_SEO_WRITE_SECRET`; план не обращается к провайдеру и не создаёт базу. Применение добавляет `--confirm TOKEN`, журнал идемпотентности SQLite фиксирует заявку в выбранной рабочей области, а повтор возвращает `status: skipped` с `reason: duplicate`. Ошибка провайдера освобождает заявку. Удаление sitemap в Bing остаётся `WRITE_DISABLED`.
- **IndexNow из sitemap.** `indexnow submit --from-sitemap [--sitemap-url ABS] [--url ABS …]` читает и разбирает sitemap только для чтения во время плана и берёт хост из `providers.bing.site`, ключ из `providers.bing.indexnow_key`, а расположение ключа — из `providers.bing.indexnow_key_location` или `https://<host>/<key>.txt`. `<urlset>` читается напрямую; `<sitemapindex>` ограничен корнем плюс пятью дочерними sitemap и 10 000 URL. URL дедуплицируются, явные `--url` добавляются первыми, URL вне хоста пропускаются. `meta.truncated`, `meta.total` и `meta.limitations` описывают усечение вместо заявления о полном инвентаре.
- **Токен плана привязан к sitemap.** Применение заново загружает sitemap; если набор URL изменился, токен аннулируется с `CONFIRM_REQUIRED` и ничего не отправляется. Стабильный sitemap отправляет обновлённый объединённый список в пределах 10 000 URL. Отсутствующий или несовпавший файл ключа — `INVALID_INPUT` с точным расположением файла, а отсутствующий `providers.bing.indexnow_key` — `AUTH_REQUIRED` на этапе плана. IndexNow остаётся только в CLI и приложении: тринадцатый инструмент MCP не добавляется.
- **MCP `seo_sitemap_submit`.** Инструмент сохраняет имя и поверхность из 12 инструментов. Входы получают необязательный `provider` (`gsc|bing`, по умолчанию `gsc`), необязательные `property` и `sitemap_url`; для Bing URL по умолчанию `<project.base_url>/sitemap.xml`. Применение Bing идёт тем же путём `SeoService.submit_sitemap`, что и в CLI. Отправка GSC и удаление Bing по-прежнему возвращают `WRITE_DISABLED`.
- **Конфигурация и поверхность.** `[providers.bing]` получает публичные `indexnow_key` и необязательный `indexnow_key_location`; API-ключ Bing Webmaster остаётся секретом и никогда не читается из `seo.toml`. 22 команды CLI верхнего уровня (15 групп и 7 команд, ни одна не добавлена и не удалена), 12 инструментов MCP (10 класса чтения: 7 чистых только для чтения и 3 инструмента, сохраняющих локальное состояние; 2 записи с воротами), 3 ресурса и 3 промпта без изменений, схема версии 4 без миграции. `schemas/tools.json` перегенерирован из-за изменения входов `seo_sitemap_submit`.

| MCP Registry | `io.github.LevapVeeskela/lv24-seo 0.9.0` опубликован |
| CI | запуск `44038720401` зелёный |

| Sitemap Bing, настроенная рабочая область | план → применение → `submitted` через JSON `SubmitFeed` |

Известные ограничения 0.9.0:

- Отправка sitemap в Bing требует API-ключа Bing Webmaster; без него план — `AUTH_REQUIRED` до сетевого вызова. Удаление sitemap в Bing остаётся `WRITE_DISABLED`.
- IndexNow требует публичный ключ и живой файл ключа по адресу `https://<host>/<key>.txt` или в настроенном месте; отсутствующий или несовпавший файл даёт `INVALID_INPUT`, и ничего не отправляется.
- Поиск sitemap ограничен корнем, пятью дочерними sitemap и 10 000 URL; URL вне хоста пропускаются, а пределы сообщаются через усечение и ограничения.
- Токен плана привязан к набору URL sitemap и живёт пять минут; изменённый sitemap требует нового плана.
- Отправка sitemap в GSC, удаление sitemap в Bing и переобход Яндекса остаются `WRITE_DISABLED`; у IndexNow нет инструмента MCP.
- Интерфейс Bing Webmaster остаётся источником истины по проблемам обхода и статусу sitemap; результат API говорит, что Bing принял, а не как быстро он переобойдёт.

## Приложение 0.7.0

Выпущено 2026-11-17. Оно добавляет панель индексации Bing, открывает официальную страницу Bing Site
Scan без заявления о запуске сканирования, генерирует посессионный секрет записи, включает
`lv24-seo 0.9.0` и поднимает `MIN_ENGINE_VERSION` до `0.9.0`, поэтому установленный движок `0.8.x`
считается несовместимым.

Что изменилось:

- **Отправка sitemap в Bing.** Экран Integrations добавляет карточку отправки sitemap, которая собирает `sitemap submit --provider bing --config <path> [--url <abs>] --allow-write [--confirm <token>] --json`. План отправляет согласие на запись, но не токен, и только выпускает план; Bing не вызывается. Карточка показывает действие, цель, сводку, хеш плана, TTL, детали payload и ограничения, а **Apply** отправляет проверенный токен. Отсутствующий ключ показывается как `AUTH_REQUIRED` с подсказкой в Settings.
- **IndexNow из sitemap.** `indexnow_submit` собирает `indexnow submit --from-sitemap --config <path> [--sitemap-url <abs>] --allow-write [--confirm <token>] --json`. Карточка показывает статус движка и число отправленных URL, а также пропущенные или дублирующиеся строки и флаг усечения. Хост, ключ и расположение ключа берутся из `providers.bing.site`, `providers.bing.indexnow_key` и `providers.bing.indexnow_key_location`; изменённый sitemap аннулирует токен плана.
- **Открытие Bing Site Scan.** У Bing нет публичного API для запуска Site Scan, поэтому `open_bing_sitescan` только открывает жёстко заданную официальную страницу `https://www.bing.com/webmasters/sitescan?siteUrl=<percent-encoded>` в браузере по умолчанию. Приложение не запускает, не опрашивает и не импортирует сканирование и никогда не сообщает, что оно началось.
- **Посессионный секрет записи.** При запуске оболочка берёт 32 байта из CSPRNG ОС, хранит 64-символьный hex `LV24_SEO_WRITE_SECRET` только в памяти Rust (обнуляется при удалении) и задаёт его каждому дочернему процессу движка после `env_clear()`. Он никогда не пишется в настройки, argv, логи, диагностику или webview. Один секрет обслуживает план и применение в сессии, поэтому старый токен плана отклоняется, и UI строит план заново.
- **Движок 0.9.0 и контракты.** Sidecar добавляет Bing `SubmitFeed` с журналом идемпотентности, IndexNow в один клик из ограниченного sitemap и новые ключи конфигурации Bing. Контракты перегенерированы из `lv24-seo 0.9.0`; входная схема `seo_sitemap_submit` получает необязательный `provider`. `MIN_ENGINE_VERSION` равен `0.9.0`, потому что движок до `0.9.0` ответил бы на новые команды `CLI_INVALID_JSON`.

Проверка, записанная для этого релиза:

| Проверка | Результат |
|---|---|
| Опубликованные артефакты | 18 на `v0.7.0` для Windows x64, Linux x64 и macOS arm64/x64, включая Windows portable `.zip.sha256` |
| Манифест обновления | `latest.json` сообщает `0.7.0` |
| CI | запуск `44041103066` зелёный |
| Релизный workflow | запуск `44043493145` зелёный |
| Обновление в приложении | `0.6.0 → 0.7.0` проверено через Rust-обновлятор на Windows NSIS: **Desktop 0.7.0**, **Engine 0.9.0** и engine ready |
| Smoke-тест рабочей области | настроенная рабочая область загрузилась в перезапущенной сборке без раскрытия данных запросов |
| Sitemap Bing | план и применение из карточки Integrations; применение вернуло `duplicate`, потому что тот же sitemap уже отправляли из CLI, поэтому журнал предотвратил повторный вызов провайдера |
| План IndexNow | `AUTH_REQUIRED`, пока нет `providers.bing.indexnow_key` и размещённого файла ключа; ни один URL не отправлен |
| Открытие Bing Site Scan | официальная страница Bing открылась в браузере по умолчанию; API не вызывался, сканирование не было заявлено запущенным |
| Секрет записи | оболочка генерировала `LV24_SEO_WRITE_SECRET` на сессию и передавала его каждому дочернему процессу движка; планы отправляли `allowWrite: true` |

Известные ограничения 0.7.0:

- Bing Site Scan запускается на странице Bing; приложение только открывает её и не запускает, не отслеживает, не отменяет и не импортирует сканирование.
- IndexNow по-прежнему требует размещённый файл ключа; при отсутствующем или несовпавшем файле ничего не отправляется.
- Отправка sitemap и IndexNow — сетевые записи к провайдеру: они не отменяемы как фоновые запуски, не повторяются автоматически и не имеют отката. Перед повтором изучите новый план.
- Токены плана привязаны к проверенному плану и сессии приложения; изменённый sitemap, новая сессия или истёкший TTL требуют нового плана.
- Отправка и удаление sitemap в GSC, удаление sitemap в Bing и переобход Яндекса остаются `WRITE_DISABLED`.
- `MIN_ENGINE_VERSION` равен `0.9.0`, поэтому движок `0.8.x` отклоняется.
- Пины sidecar для Linux и macOS остаются `null`; релизный гейт опирается на rebuild-aware отчёты.

## Движок 0.8.0

Выпущен 2026-11-16. Он добавляет запись Core Web Vitals, аутентификацию Google Search Console через
сервисный аккаунт, более богатые индикаторы Яндекс.Вебмастера, недеструктивное `backup restore --to`,
жизненный цикл планировщика и два исправления провайдеров. В CLI теперь 22 команды верхнего уровня;
поверхность MCP остаётся в 12 инструментов, схема SQLite — версия 4.

Что изменилось:

- **Запись CWV.** `cwv collect --url ABS [--url ABS …] [--device phone|desktop|tablet|all] [--source crux|psi|both] [--limit 1..50]` — писатель, стоящий за недельным разделом `cwv`. CrUX опрашивается по каждому URL и устройству (`mobile` — псевдоним `phone`), и каждый полученный p75 становится полевой строкой `metric_daily` (`source=crux`, `scope`, `key=<абсолютный URL>`, `metric`, `value`, дата получения в `report.timezone`, `accuracy=crux_field_28d`). Строки PSI остаются в `data.lab` и никогда не сохраняются, поэтому лабораторная оценка не может загрязнить полевой ряд; каждый запуск с PSI сообщает `cwv_lab_ignored`, а у PSI нет `tablet`, поэтому `tablet` пропускается как `psi_tablet_unsupported`. CrUX — скользящее окно 28 дней, поэтому `meta.data_age_days` не меньше 2; URL с низким трафиком получает `low_traffic` и не пишет строку, а не ноль. `--limit` ограничивает URL 50 (по умолчанию 10); `meta.total`, `meta.processed`, `meta.pairs_total`, `meta.pairs_processed` и `meta.calls` делают предел явным, а усечённый запуск ставит `meta.truncated: true` с `cwv_url_cap`. CrUX требует ключ (`AUTH_REQUIRED` до любого вызова), а сохранение — хранилище (`CONFIG_INVALID`). `report weekly` и `seo_weekly_report` читают сохранённые строки CWV по сегодняшний день, поэтому сбор попадает в тот же запуск.
- **Сервисные аккаунты GSC.** Читаются `providers.gsc.service_account_file` (абсолютный путь) и `LV24_SEO_GSC_SERVICE_ACCOUNT_FILE`; файл важнее сохранённого `gsc_token`, а окружение важнее файла. `gsc_token`, являющийся JSON-объектом сервисного аккаунта (`type: service_account` плюс `private_key`), тоже принимается. Адаптер подписывает RS256 JWT (`iss`, `scope=webmasters.readonly`, `aud`, `iat`, `exp`), обменивает его в `token_uri` ключа по JWT-bearer grant и обновляет за 60 секунд до истечения; обычный токен сохраняет историческое поведение `Authorization: Bearer` и не обновляется. `properties` сообщает `token_source: service_account_file|secret|missing` и помечает GSC готовым; `doctor` добавляет некритичную проверку `gsc_auth`. Ни один из них не печатает JSON или приватный ключ, а `auth status` по-прежнему смотрит только keychain, окружение и файловые секреты. Относительный, отсутствующий, нечитаемый или невалидный файл — `CONFIG_INVALID`; отклонённый обмен — `AUTH_INVALID`, и тело ответа никогда не повторяется. Теперь требуется `cryptography>=43` (Apache-2.0 OR BSD-3-Clause).
- **Более богатые индикаторы Яндекса.** `yandex queries` и `yandex_query_performance` показывают `avg_click_position` рядом с показами, кликами и позицией, возвращают `query_id`, когда провайдер его присылает, и сохраняют неизвестный индикатор в `extra_indicators` вместо отбрасывания строки; устаревшая списочная форма `indicators` по-прежнему принимается. `yandex indexing` и `yandex_indexing_state` объединяют серию `indexing/history` (`HTTP_2XX` … `OTHER`, в любом регистре) в одну строку на дату (`http_2xx` … `other`); пропущенная серия остаётся отсутствующей, а неизвестные серии сохраняются в `extra_indicators`. `summary.site_problems` несёт соответствие серьёзность → количество рядом с существующими счётчиками, а пропущенный счётчик остаётся отсутствующим, а не становится `0`.
- **Недеструктивное восстановление.** `backup restore --file ABS --to ABS_DIR` распаковывает архив в новый каталог и никогда не трогает текущую рабочую область. Архив перепроверяется точно как при плане на месте (манифест, набор и имена членов, размеры, каждый SHA-256). Цель должна быть абсолютным путём, которого не существует, с существующим родителем; существующая, непустая или символическая цель — `INVALID_INPUT` и никогда не объединяется и не перезаписывается. Абсолютные пути, `..`, обратные слэши и символические ссылки внутри архива отклоняются до распаковки, база проходит `PRAGMA quick_check` до и после перемещения на место, а staging-каталог удаляется. Архив без базы даёт каталог только с конфигурацией, `database.in_archive: false` и явное предупреждение; пустая база не выдумывается. `--allow-write` и токен не участвуют; передача любого из них с `--to` или `--to` с `--config` — `INVALID_INPUT`. Двухфазное восстановление на месте не изменилось.
- **Жизненный цикл планировщика.** `schedule install` по умолчанию только планирует: печатает блок cron, пользовательские unit-файлы systemd или XML Планировщика заданий плюс команду, которую он запустит, с `dry_run: true` и `installed: false`. Ничего не пишется до `--allow-write`; `--print` остаётся синонимом плана и важнее `--allow-write`. Сгенерированные задания содержат абсолютный путь `--config` и запускаются из каталога конфигурации. `schedule status` только читает и сообщает `installed|outdated|partial|missing|unknown`, ожидаемые пути и `exists`/`matches` по артефактам; `unknown` означает, что планировщик хоста не удалось проверить, и `matches` тогда `null`. `schedule uninstall` по умолчанию только планирует, а с `--allow-write` удаляет ровно свой управляемый блок cron, два unit-файла `<job>.service`/`<job>.timer` или именованную задачу; повторный запуск — no-op (`removed: false`, `state: missing`), а чужие строки и задачи никогда не трогаются. Блок cron, потерявший конечный маркер, чинится консервативно, и конверт предупреждает.
- **Исправления.** Yandex Metrika `stat/v1/data` теперь отправляет документированный 1-based `offset`; прежний `0` отклонялся с HTTP 400 на каждом вызове, из-за чего карточка Метрики выглядела настроенной, но пустой. Пагинация сдвигается на уже возвращённые строки. Вывод CLI `--json` ASCII-экранируется, а человеческий вывод заменяет непечатаемые глифы вместо падения, поэтому завершённый отчёт, перенаправленный в устаревшую кодировку Windows (cp1251/cp866), больше не падает с `UnicodeEncodeError` при печати предупреждения.

Путь должен быть абсолютным и обычным файлом; glob, UNC/device-пути и большие файлы падают с `INVALID_INPUT` до чтения. Файл открывается только для чтения и никуда не отправляется и не сохраняется.
- **12-й инструмент MCP.** `seo_log_analysis(file, bot="")` только читает (`readOnlyHint: true`, `writes_local_state: false`), не требует сервиса, хранилища или рабочей области и возвращает те же `data`, `meta` и `warnings`, что и CLI.
- **Атрибутированный дайджест.** Когда два окна GSC сопоставимы и в хранилище есть проблемы обхода или страницы, недельный отчёт добавляет раздел `Attributed change digest`: каждое значимое изменение получает предполагаемую причину (`new_crawl_issue`, `resolved_crawl_issue`, `indexing_event`, `page_state`, `unexplained`), уверенность, до трёх строк доказательств и `next_action`. Без доказательств пункт остаётся `unexplained` с ограничением; пунктов не больше 8, доказательств — 3 на пункт.
- **Жизненный цикл задач (схема v3).** `tasks list`, `tasks add` и `tasks update` управляют находками с ключом `(kind, property_id, url, rule_id)` и состояниями `open`, `in_progress`, `verified`, `dismissed`. `add` идемпотентен и сообщает `created`, `existing` или `reopened`; подтверждённая находка при повторном обнаружении переоткрывается, отклонённая остаётся отклонённой. Принимаются только документированные переходы, `list` идёт от новых к старым и ограничен (1–1000, по умолчанию 200), `--payload` отклоняет ключи, похожие на учётные данные. Миграция аддитивная.
- **Переносимый backup.** `backup create --out ABS [--force]` пишет `lv24-seo-backup-YYYYMMDDTHHMMSSZ.zip` с `manifest.json` (размеры и SHA-256 каждого члена), отредактированным `seo.toml` с `storage.data_dir`, сброшенным в `./data`, и согласованной копией `data/seo.sqlite3`, сделанной через SQLite backup API. Секреты, токены, логи и кэши не включаются; источник только для чтения, архив пишется атомарно. Восстановление не реализовано.
- **Поверхность и схема.** 20 команд CLI верхнего уровня (13 групп и 7 команд), 12 инструментов MCP (10 класса чтения, включая `seo_log_analysis`, плюс 2 записи с воротами, которые всё ещё возвращают `WRITE_DISABLED`), 3 ресурса и 3 промпта без изменений. Версия схемы — 3; `ReportSection` получил необязательные поля `total`, `truncated` и `data_age`, а параллельное первое открытие повторяет переключение WAL вместо падения на `SQLITE_BUSY`.

## Движок 0.5.3

Выпущен 2026-11-16. Он делает записи агентов двухфазными, уводит обход с event loop MCP,
добавляет код выхода `--strict` для CI и заменяет общие сбои хранилища типизированными кодами. Без
миграции схемы, без новых CLI-команд и MCP-инструментов: поверхность остаётся в одиннадцать
инструментов, меняются входы, коды выхода и коды ошибок.

Что изменилось:

- **Двухфазные записи MCP.** `seo_recrawl_request` и `seo_sitemap_submit` принимают `allow_write` (по умолчанию `false`), `plan_hash` и `confirm_token`. Вызов без токена — это dry run, возвращающий план, его хеш и токен на 300 секунд; применение должно повторить хеш и токен. Несовпадающий хеш даёт `CONFIRM_REQUIRED`, повтор возвращает `status: skipped` с `reason: duplicate`, а ошибка провайдера освобождает заявку, поэтому повтор разрешён. `LV24_SEO_WRITE_SECRET` обязателен; пустой секрет — это `WRITE_DISABLED`. В поставляемом `SeoService` по-прежнему нет адаптера записи для переобхода или карты сайта, поэтому оба инструмента возвращают `WRITE_DISABLED` даже с `allow_write=true`: контракт есть, вызова провайдера нет.
- **Обход вне event loop.** `seo_crawl_site` идёт в рабочем потоке с собственным короткоживущим хранилищем и жёстким бюджетом 600 секунд. После бюджета клиент получает повторяемый `UPSTREAM_UNAVAILABLE` с предложением меньшего `max_urls`; поток завершается в фоне, а сервер продолжает отвечать другим инструментам. Остальные инструменты остаются сериализованными на owner loop.
- **`--strict` и код 5.** `stats`, `gsc query`, `yandex queries`, `yandex indexing`, `crawl`, `report weekly` и `report diff` принимают `--strict`. `meta.strict` выставляется всегда; усечённый ответ остаётся `ok: true`, но выходит с `5`, а `meta.limitations` объясняет, чего не хватает. Без флага усечение по-прежнему выходит с `0`. `report diff --markdown` соблюдает тот же код.
- **Журнал записи следует за `--config`.** Применение записи открывает журнал идемпотентности из каталога данных выбранной рабочей области, поэтому `--config /srv/site/seo.toml` записывает заявку в `/srv/site/data`, даже если оболочка в другом месте. Раньше журнал разрешался от рабочего каталога, что молча отключало защиту от повтора.
- **Типизированные ошибки хранилища.** `STORE_LOCKED` (повторяемая), `STORE_CORRUPT` (с `detail.backup_path`) и `STORE_UNAVAILABLE` заменяют общий конверт `INTERNAL`. Повреждённый файл копируется рядом с собой до любых других действий; оригинал никогда не перемещается и не удаляется. Все три кода выходят с `1`, как `INTERNAL`.
- **Честные данные провайдеров.** Усечённый результат GSC не содержит `total` вместо точного числа рядом с `truncated: true`, а `data_age_days` не меньше документированной задержки 3 дня. `limit` Metrika — это размер страницы: клиент листает `offset` до 10 000 строк и 100 страниц, помечает полную страницу без `total_rows` как усечённую и никогда не листает агрегатный вызов. Bing берёт `data_age_days` из даты самой новой строки вместо жёсткого нуля. Загруженный хост Yandex с пустой историей возвращает `total: 0` с `empty_history`, а не `degraded_host`, и обычный `count` Webmaster больше не принимается за общий итог.
- **Область карты сайта.** `<loc>` вне собственных origin карты сайта (origin стартовой карты плюс конечный origin каждого прочитанного документа) отбрасывается и один раз сообщается как `off_origin_loc`, поэтому индекс никогда не уведёт читателя на другой сайт.
- **`doctor` считает объявленный каталог данных критичным.** Когда конфиг или `LV24_SEO_DATA_DIR` задаёт каталог, отсутствующий или непригодный каталог валит проверку; `meta.data_dir_declared` сообщает, какой это случай.
- **Мелкие исправления.** Crontab с незавершённым управляемым блоком чинится консервативно: удаляются только строки, похожие на записи lv24-seo, а предупреждение просит оператора проверить `crontab -l`. Обход соблюдает один `429` `Retry-After`, а не считает троттлинг ответом страницы.

| npm | `@lv24/seo 0.5.3` опубликован с тегом `latest` |

  нужно читать из `error.code`.

- `doctor` считает непригодный объявленный каталог данных критичным, поэтому намеренно отсутствующий каталог теперь
  валит проверку, а не предупреждает.

движок `0.5.2` по-прежнему принимается.

Что изменилось:

- **Обновлятор перенесён в Rust.** В списке возможностей webview только `updater:allow-check`. `update_install` заново проверяет endpoint, отказывается от версии, отличной от объявленной панелью (`UPDATE_VERSION_MISMATCH`), скачивает, проверяет подпись и запускает установщик; прогресс приходит как `update://progress`. `update_cancel` отбрасывает загрузку до запуска установщика и возвращает `UPDATE_CANCELLED`; после начала установки он возвращает `false`, и панель остаётся как есть.
- **Путь конфигурации, одобренный диалогом.** `pick_config` записывает файл, возвращённый нативным диалогом; `settings_set` принимает только активный или одобренный путь и отклоняет остальное с `PATH_NOT_APPROVED`. UNC-шара, устройство `\\?\` или `\\.\` в `storage.data_dir` отклоняется с `INVALID_PATH` и `detail.reason: network_or_device_path` до разрешения.
- **Редактирование и таймауты.** stderr движка редактируется до того, как попасть в webview, лог или диагностический пакет, причём до усечения 300-символьного превью. Ошибка TOML-парсера тоже редактируется. Вспомогательная задача сверх бюджета падает с `PATH_TIMEOUT`, а не подвешивает экран.
- **Рабочая область и состояние UI.** `shell_status` сообщает `configExists`; перемещённый или удалённый конфиг показывает баннер отсутствующей рабочей области с **Choose config** вместо общей ошибки статистики. У блоков провайдеров есть явный переключатель включения — единственный писатель `providers.<id>.present`. Валидация трёхзначна (`valid`, `invalid`, `skipped`), поэтому двойной клик или переключение рабочей области больше не сообщают о валидном черновике как о невалидном. Skip-link сохраняет hash-маршрут, а маршрутный error boundary локализует сбой рендера и предлагает перезагрузку.
- **Релизный конвейер.** CI на pull request запускает тесты релизных скриптов; матрица Rust включает Intel macOS runner, который использует релиз; Rust закреплён на `1.95.0`. `latest.json` валидируется по `contracts/latest.schema.json` до создания черновика. Один протестированный список управляет файлом контрольных сумм и списком загрузки, а Windows portable ZIP поставляется с sidecar `.sha256`, который релизный гейт пересчитывает и сравнивает.

## Движок 0.5.2

Это bugfix-релиз линии 0.5.x. Он закрывает блокеры, найденные после 0.5.1: относительный
`storage.data_dir` в `seo.toml` следовал за рабочим каталогом оболочки, CLI собирал write-gate без
журнала идемпотентности, ошибки загрузки sitemap эхом возвращали URL с query-токенами, а GSC
заявлял полное покрытие, когда последняя страница ровно заполняла лимит строк.

Без миграции схемы и без новых CLI-команд или MCP-инструментов. JSON-конверт сохраняет прежние
ключи; `doctor` добавляет аддитивные поля `meta.data_dir` / `meta.data_dir_source` и может нести
предупреждение. Существующие хранилища открываются без изменений, а конфиги с абсолютным
`data_dir` работают как раньше.

Что изменилось:

- **Привязка data-dir.** Относительный `storage.data_dir` из `seo.toml` теперь разрешается
  относительно каталога этого файла, поэтому `lv24-seo --config /srv/site/seo.toml` использует
  `/srv/site/data` из любого рабочего каталога. `init` создаёт `<config dir>/data` и пишет
  `data_dir = "./data"`. Встроенное значение по умолчанию (без блока `[storage]`) и
  `LV24_SEO_DATA_DIR` намеренно остаются привязанными к процессу. `doctor --json` сообщает
  `meta.data_dir` и `meta.data_dir_source` (`config` или `working directory`), а
  `config show --json` показывает эффективный путь.
- **Абсолютные пути планировщика.** `resolve_config_path` всегда возвращает абсолютный
  нормализованный путь. `schedule install` и `schedule print` встраивают абсолютный аргумент
  `--config` и используют родительский каталог конфига как рабочий каталог, поэтому задание
  запускает тот же конфиг из любого каталога планировщика.
- **Повторобезопасные записи CLI.** Команда записи с `--confirm` открывает SQLite-журнал рабочей
  области и передаёт его в `WriteGate`. Повторный токен возвращает `status: skipped` с
  `reason: duplicate`, и провайдер вызывается ровно один раз. Dry run не открывает журнал и не
  создаёт базу. Без инициализированной рабочей области команда всё равно работает, но конверт
  предупреждает, что защита от повтора отключена на пять минут жизни токена.
- **Маскирование URL в предупреждениях sitemap.** Неудачная загрузка sitemap сообщает только тип
  исключения (`HTTPError`, `TimeoutError`, …), но не URL и не query-строку. Сбой остаётся
  видимым и машиночитаемым, но `?key=…` не попадает в предупреждения, `limitations[]` или
  MCP-полезную нагрузку.
- **Честность точного лимита GSC.** Последняя страница GSC, которая ровно заполняет лимит в
  50 000 строк, помечается `truncated: true` с `rows_cap_50000`; меньший лимит вызывающего даёт
  предупреждение с его значением. Нулевой лимит считается лимитом, а не пустым результатом.
  Полная страница не доказывает, что за лимитом нет строк.
- **Опциональное маскирующее логирование.** `LV24_SEO_LOG_LEVEL` устанавливает redacting-handler
  ровно в двух точках входа: callback CLI и `lv24-seo mcp serve`. Если переменная не задана,
  конфигурация логирования вызывающего не меняется. Вывод — одна JSON-строка на запись, когда
  stderr не терминал (pipe, лог планировщика, MCP-хост), и обычная строка в терминале.
  MCP-транспорт пишет только в stderr; stdout остаётся протоколом.
- **Мелкие исправления.** Pending-заявка записи после падения по-прежнему не имеет TTL; удаление
  `data/seo.sqlite3` сбрасывает журнал; `doctor` не падает на относительном data-dir.

Проверки этого релиза:

| Проверка | Результат |
|---|---|
| Офлайн-набор тестов | 1141 passed, 1 skipped |
| `ruff check` | Чисто |
| `ruff format --check` | Чисто |
| `mypy src` | Чисто |
| MCP registry `--check` | Чисто (поверхность не менялась) |

Известные ограничения 0.5.2:

- Конфиг, открытый через symlink, привязывает data-dir рядом со ссылкой, а не с целью: symlinks
  намеренно сохраняются. `LV24_SEO_DATA_DIR` остаётся process-scoped переопределением.
- Pending-заявка записи после падения не имеет TTL и считается выполняющейся, пока оператор её не
  освободит. Это намеренно: ложный повтор может дублировать запись провайдера.
- Без data-dir защиты от повтора нет; токен остаётся валидным все пять минут.
- Сайт ровно с 50 000 строк GSC и без строк за лимитом тоже помечается truncated. Это намеренно:
  полная страница не доказывает отсутствие следующей строки.
- Логирование остаётся опциональным. Правила редактирования покрывают чувствительные ключи,
  известные префиксы токенов и длинные непрозрачные значения, но не каждый формат секрета
  конкретного провайдера.

### Очистка sidecar перед обновлением

Sidecar движка лежит внутри установленного каталога ресурсов, поэтому запущенный процесс
`lv24-seo` держит файл заблокированным и NSIS-установщик не может его заменить. Перед запуском
установщика оболочка вызывает `prepare_update`, который останавливает **только те PID движка,
которые зарегистрировал этот экземпляр приложения** при их запуске. Ничего не ищется по имени
образа, поэтому другая установленная копия, portable-сборка, запущенный в терминале `lv24-seo`
или посторонний процесс не затрагиваются. Короткое ожидание (2 с) подтверждает завершение.

Если очистка не удалась, установка блокируется с `UPDATE_ENGINE_BUSY`, а не запускает установщик,
который сломается на середине. Ошибка повторяемая: закройте запуск, удерживающий sidecar, и
нажмите кнопку снова.

### Секреты и конфигурация

- Yandex Metrika сохраняет собственный auth-провайдер (`metrika`, `yandex_metrika_token`) в списке
  провайдеров, бейдже Settings, окне секретов и подписях en/ru/zh. Он никогда не берёт токен
  Webmaster.
- Приложение и CLI используют **одну запись OS keychain на провайдера** (сервис `lv24-seo`).
  Токен, введённый через `lv24-seo auth set --provider <p> --stdin` в терминале, появляется в
  `auth status` приложения без повторного ввода, а токен из приложения виден CLI.
- Токен из `LV24_SEO_*` показывается в UI как **read-only**: приложение не может удалить переменную
  окружения и говорит об этом, а не предлагает кнопку удаления, которая ничего не делает.
  `auth logout` с `deleted: false` показывается честно.
- Состояние workspace, отчёта, doctor и секретов очищается при смене workspace или переходе движка
  в offline. Действия, которые не могут работать, отключаются, а не падают по клику. Каталоги
  сообщений en/ru/zh согласованы; отсутствующий ключ — ошибка теста.
- Запись конфигурации и настроек атомарна **и fsynced** (файл и родительский каталог). Временные
  черновики и резервные копии имеют режим `0600`; чтение конфига ограничено 8 MiB; настройки
  загружаются по полям; зарезервированные имена Windows и завершающие точки/пробелы отклоняются
  в каждом компоненте пути. stderr валидации конфигурации редактируется до попадания в UI или лог.

## Релизный конвейер

Workflow приложения ручной и owner-gated. У него нет триггеров push, pull-request или tag. Владелец

## Пин sidecar и контрольные суммы

Релизный sidecar — дерево PyInstaller **onedir**, собранное на соответствующем хосте; PyInstaller не
кросс-компилирует. Версии движка, Python, Pydantic, Typer и PyInstaller закреплены в
`scripts/cli-checksums.json`. `0.7.0` закрепляет движок `0.9.0` (выше `0.8.0`), Python `3.12`, Pydantic `2.14.3`,
Typer `0.29.0` и PyInstaller `6.22.3`.

Вывод PyInstaller onedir не байт-воспроизводим. Поэтому политика контрольных сумм разделена:

- **Локальная релизная сборка — строгая.** `scripts/verify-sidecar.mjs` должен совпасть с
  закоммиченными SHA-256 и размером; `--write` обновляет пин после ревью. `null` означает
  «ещё не проверено», а не «проверено».
- **CI-пересборка — rebuild-aware.** Job сборки запускает верификатор с `--no-hash` и записывает
  фактический SHA-256 в `release/sidecar-checksums-<target>.json`.
- **Релизный гейт — по отчётам.** Релизный job требует валидный отчёт для каждого отгружаемого
  target: совпадение имени target, `hashPolicy: "rebuild"`, `ok: true`, 64-hex хеш, положительный
  размер и точную версию движка.

Для `0.9.0` Windows x64 имеет проверенный локальный пин; sidecar для Linux и macOS пересобраны релизным
workflow с пройденными rebuild-aware отчётами, а их проверенные пины остаются `null`, пока локальная сборка
не будет проверена на этих хостах. Windows-пин `0.8.0`
не переносился, потому что исполняемый файл меняется вместе с движком. Отчёты контрольных сумм — доказательства CI, а не релизные артефакты.
`SHA256SUMS.txt` покрывает установщики, пакеты обновления, подписи и `latest.json`; исполняемый
файл sidecar находится внутри этих пакетов и отдельно не указан. При ручной установке сверяйте
скачанный артефакт с `SHA256SUMS.txt`.

```bash
node scripts/verify-sidecar.mjs \
  --root src-tauri/engine \
  --target x86_64-pc-windows-msvc \
  --engine-version 0.9.0
```

## `latest.json`, подпись и публикация

Подписи обновлений используют бесплатный ключ Ed25519/minisign, отдельный от подписи кода ОС.
Публичный ключ встроен в приложение; приватный — секрет репозитория, передаваемый только на шаг
сборки. Включён `requireSignedVersion`, поэтому объявленная версия привязана к подписанному пакету.
Обновление принимает только версию выше текущей, поэтому откатиться нельзя.

`scripts/stage-release-assets.mjs` выравнивает и нормализует имена пакетов и пишет метаданные
`updater-<platform>.json` для каждой платформы. `scripts/merge-latest-json.mjs` объединяет их в
`latest.json`:

- обязательные generic-ключи: `windows-x86_64`, `linux-x86_64`, `darwin-aarch64`,
  `darwin-x86_64`;
- bundle-алиасы, которые проверяет обновлятор: `windows-x86_64-nsis`, `linux-x86_64-appimage`,
  `darwin-aarch64-app`, `darwin-x86_64-app`;
- необязательные `linux-x86_64-deb` и `linux-x86_64-rpm` только если Tauri создал их подписи;
- каждый URL указывает под `releases/download/<tag>/`;
- каждая подпись сверяется с файлом `.sig` на диске;
- каждый упомянутый артефакт должен существовать;
- примечания берутся из `docs/releases/<version>.md`, если файл есть.

Релиз сначала создаётся как **draft**. Артефакты загружаются, пока он draft, `latest.json` —
последним, затем job публикует через `gh release edit --draft=false` и проверяет удалённые имена
артефактов. `releases/latest/download/latest.json` разрешается только на опубликованный релиз,
поэтому пользователи не видят частично загруженный манифест. Повторный запуск переиспользует
существующий draft, очищает его артефакты и отказывается перезаписывать опубликованный релиз.

## Закрепление версий

Версия приложения должна совпадать в `package.json`, `src-tauri/tauri.conf.json`,
`src-tauri/Cargo.toml`, Git-теге и заголовке релиза. Пин движка живёт в
`scripts/cli-checksums.json`; workflow передаёт `engine_version` явно, а релизный гейт требует
совпадения с манифестом.

`MIN_ENGINE_VERSION` в `src-tauri/src/commands.rs` в текущем исходнике равен `0.9.0`. Сборка `0.7.0`
включает движок `0.9.0`, поэтому минимум совпадает с движком сборки, а движок `0.8.x` считается
несовместимым. Оболочка
принимает движок не старше этой версии и помечает более старый как offline с уведомлением. Более
новый движок проходит гейт, но не является релизно-проверенным пином. Сборочная версия может
использовать `LV24_SEO_BIN` с другой версией; UI помечает его внешним и всё равно проверяет
минимум. Движок из `PATH` используется только при `LV24_SEO_ALLOW_PATH_ENGINE=1`.

## Однократное обновление с 0.1.0

У `0.1.0` нет updater, endpoint и публичного ключа. Он не может найти или установить `0.7.0`.
Скачайте и установите `0.7.0` вручную один раз (NSIS-установщик или portable ZIP в Windows).
После этого установка `0.7.0` может автоматически обновляться до следующих релизов, если
использует пакет с поддержкой автообновления.

## Откат

Автоматического отката нет. Откат — ручная установка более старого релиза.

| Сбой | Действие |
|---|---|
| Плохой установщик, но рабочее приложение | Выпустить исправленный патч; не перезаписывать артефакты под тем же тегом |
| Плохой `latest.json` | Выпустить исправленный патч; draft-гейт не даёт частичному манифесту стать видимым |
| Скомпрометированный ключ обновлений | Ротировать ключ, выпустить ручной релиз с новым публичным ключом; автообновление не переживает ротацию |
| Регрессия движка | Закрепить предыдущую версию движка, пересобрать и выпустить патч |
| Нужна старая сборка приложения | Установить вручную; обновлятор отказывается от понижения |

Не перемещайте и не переиспользуйте опубликованный тег. Держите артефакты предыдущего релиза
доступными для отката. Если endpoint нужно отключить, выпустите ручной релиз и задокументируйте это.

## Проверка загрузки

`SHA256SUMS.txt` покрывает каждый опубликованный артефакт. Проверьте файлы, которые собираетесь
устанавливать:

```bash
sha256sum -c SHA256SUMS.txt --ignore-missing
```

На macOS `shasum -a 256 -c SHA256SUMS.txt` доступен в базовой системе. В Windows сравните
`Get-FileHash <file> -Algorithm SHA256` с соответствующей строкой. Не запускайте файл, хеш которого
не совпадает.

По умолчанию пакеты ОС не подписаны (Windows, Linux) или подписаны ad-hoc (macOS). Подпись
обновления аутентифицирует обновления, а не первую ручную загрузку. Предупреждения SmartScreen и
Gatekeeper ожидаемы; сверьте контрольную сумму и используйте документированный путь
**More info → Run anyway** или **Open Anyway**. Не отключайте эти защиты глобально.

См. [Безопасность и приватность](/ru/security/) для доверия к обновлениям и [Архитектуру](/ru/architecture/) для раскладки sidecar.
